# 142. 模块流程与单模块讨论排期

> 2026-11-12。点子王 × 行为学家 × 总控 × 项目经理 × MC 专家。  
> 目的：定模块流程、写权限、闭环顺序，再逐模块打磨。

## 1. 先钉死：A 的层级归属

```text
原滑动树 A1–A5：
  A1 日目标 / A2 领域排班
  在融合架构里已由 B 账本 + 外层档位接管

A 实际保留：
  A3 方法选择
  A4 目标实例
  A5 原子执行
```

结论：

```text
A 不是完整 A1–A5 调度器。
A = 当前焦点内的执行树。
A1/A2 归 B + 外层档位。
```

不钉死这条，后面评审会各说各话。

## 2. 最终模块流程

```text
B 账本
  承诺 / 债 / 进展 / deadline 窗口
  唯一写者
        │
        ▼
外层档位
  tier / commitment / policy
  只做档位与过滤，不排方法
        │
        ▼
方法库
  按 focus 谓词 + 事实生成 eligibleMethods
        │
        ▼
allowedMethods 交集
  方法库 eligible ∩ 外层 policy
        │
        ▼
内层排序
  只在 allowedMethods 内排
        │
        ▼
A 执行树
  当前焦点内选/抢/下滑
  输出 intent + commitmentId
        │
        ▼
执行器
  actionLock / atom / postcheck
  唯一执行事实写者
        │
        ▼
result event
        │
        ▼
B 账本派生进展/债/状态
```

单向环：

```text
B → 外层 → 方法库 → 内层 → A → 执行器 → B
```

## 3. 三条被圆桌纠正的点

### 3.1 A 的 intent 必须带 commitmentId

否则 result 回 B 无法归因，进展/债断链。

### 3.2 allowedMethods 不是外层生成

```text
方法库：按焦点谓词 + 前置事实生成 eligibleMethods
外层：只提供 policy/allowed 过滤
内层：只在交集内排序
```

否则外层变成第二调度器。

### 3.3 结果事件必须可判负

最少字段：

```text
eventSeq / txId / atomId / planId / commitmentId
gameTick / snapshotSeqBefore/After
methodId / paramsHash
status {ok,failed,preempted,refused,timeout,slot_blocked,cancelled}
postcheck {blockBefore/After,itemDelta,pos,hp,hunger,inWater/onGround}
failureClass / refusedReason
sameParamCount / preemptReason / latchHit
```

硬规则：

```text
postcheck 只能执行器写
paramsHash 必须有（同参≤2 判定）
```

## 4. 承诺生命周期

```text
proposed
  → active
  → blocked ⇄ active
  → done | failed | abandoned | expired
```

唯一写者：B。

其他模块：

```text
外层：只读 + 输出档位/过滤
方法库：纯数据
内层：只排序
A：只发 intent + commitmentId
执行器：只发 result event
```

状态确认：

```text
ready/started/progressed/satisfied
必须由执行事件 + postcheck 支撑
B 不能自己把 pending 改 satisfied
```

## 5. 闭环优先，不按模块加厚

总控意见：

```text
先跑通一个承诺的完整生命周期：
建立 → 选择 → 执行 → 回写 → 完成/放弃
再分别加厚债本、再入、多层打分
```

禁止：

```text
先补某一层，再连闭环
```

## 6. 单模块讨论顺序

### Session 0：跨模块契约

```text
result event 语义
承诺生命周期
写权限
A 的层级归属
intent 必须带 commitmentId
```

### Session 1：执行器与结果事件

```text
actionLock / atom 边界 / postcheck
result 字段 / failureClass / paramsHash
```

### Session 2：B 最小账本

```text
一条承诺
状态机
进展/债派生规则
```

### Session 3：方法库与 allowedMethods

```text
节点 schema
eligibleMethods 生成
外层 policy 过滤
```

### Session 4：外层档位

```text
tier 分类
deadline 窗口
档位防饿死
```

### Session 5：内层排序

```text
expectedProgress / cost / risk / reversibility
failure history
```

### Session 6：A 执行树

```text
焦点内选择/抢占/下滑
intent 队列
原子边界
```

### Session 7：可见状态

```text
意图—动作—结果
waiting / 预备下一步
不显示分数/档位/账本术语
```

## 7. 可见状态原则

玩家只看到：

```text
它打算做什么
现在在做什么 + 一句为什么
做成了/没成，换办法
```

不显示：

```text
分数
tier
allowedMethods
候选列表
债本/进展账/日结术语
```

不能造假：

```text
说做 X 实际做 Y
等待说成进行中
计划说成完成
谓词未真说达成
```

## 8. 流程判负

```text
A 的 intent 缺 commitmentId
B 状态变更无 result event + postcheck 支撑
非唯一写者改承诺状态
外层生成 allowedMethods（越过方法库）
玩家可见状态与实际 focus/atom 不一致
任何进展/债变化无法追溯到三元组：
  result event + 谓词证据 + commitmentId
```

## 9. 一句话

```text
这不是六个独立模块，
是一条“承诺 → 档位 → 方法 → 焦点 → 执行 → 回写”的闭环流水线。
先让一个承诺走完全程，再逐模块加厚。
```
