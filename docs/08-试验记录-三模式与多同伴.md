# 试验记录：三模式行为树 + 多同伴（2026-11-07 19:30–20:00）

> 用户出门约 1 小时，交给树进程自行完成的三项试验。
> 环境：Minecraft 1.21.1 NeoForge，求生模式，雪原（snowy_plains），主人 AFK。

---

## 一、三种行为模式

### 1.1 设计

| 模式 | 做什么 | 触发条件 |
|---|---|---|
| **survival**（默认） | 只保命 + 跟着主人 | 血低撤退、饿了好吃、太远牵引 |
| **production** | 挖资源 | 循环尝试方块列表；连续 4 次找不到 → 出去探索 30 秒 |
| **combat** | 主动清怪 | 观测到 16 格内有敌对生物就打最近的 |

**仲裁顺序**（全部是固定规则，不做判断）：

```
生存检查（血 ≤ retreatHp / 饿 ≤ eatHunger）
   ↓ 没触发
模式行为（combat 打怪 / production 采集）
   ↓ 没触发
牵引绳（离主人 > maxDistance 就回去）
   ↓
待命
```

每种自动行为有独立冷却，失败后按类型拉长冷却（gather 6 秒换下一种；其它 2 倍冷却）。

### 1.2 实测证据

**生存（饿）**：

```
auto_action eat(饿) -> eat {}
failed  g1 eat not_found: no food in inventory
say_line task_failed: 有点麻烦，找不到
auto_action_backoff eat 失败，60s 后再试
```

**生产（轮换 + 探索兜底）**：

```
gather(production:oak_log)    → not_found
gather(production:birch_log)  → not_found
gather(production:spruce_log) → not_found
gather(production:stone)      → failed（没有镐子，挖了也不掉）
explore(production:找不到资源，出去探) -> explore {seconds:30}
```

6 秒一个方块类型，4 次失败后自动出去探 30 秒——这条链路**完整跑通**。

**模式切换（按同伴独立）**：

```
control helper   --op mode --mode combat     → mode=combat
control tyrander --op mode --mode survival   → mode=survival
```

25 秒后：helper 保持 combat 且**没有乱动**（周围无敌对）；tyrander 回 survival 后继续处理饥饿。

**战斗模式**：⚠️ **未能实测**——测试时是白天、16 格内 `hostileCount=0`，仲裁器正确地没有下任何指令。
只验证了 `fight_nearest` 技能本身可加载、可下发（空目标时快速返回 `{none:true}`）。
真正的战斗行为需要在有怪时复测。

## 二、多同伴

### 2.1 创建与自动接管

通过 MCP 直接 `create_companion("helper")`（不经过树），树在 **5 秒内自动发现并接管**：

```
tyrander:production dist=3.7
helper:survival     dist=3.3
```

**结论：新增同伴不需要重启树，也不需要改配置。**

### 2.2 并发验证

同时给两个同伴下不同目标：

```
tyrander → go_to {x:20,  z:10}
helper   → go_to {x:-20, z:10}
```

2 秒后：**两边都 `busy=true`**（同时在跑）。

结果：

| 同伴 | 结果 | 位置 |
|---|---|---|
| helper | 3.5 秒到达 | (-16.5, 69, 10.4) |
| tyrander | 期间在跑 production 的 explore，go_to 排在后面，最终到达 20 格方向 | (22.5, 68, 8.5) |

**结论：**

- **跨同伴并发成立**：一个同伴在执行长任务时，另一个同伴的目标照常执行；
- **同一同伴严格串行**：后下的目标排队，不会互相打断；
- 这与 mod 的设计一致（Lua 执行槽是**按同伴**的，不是全局的）。

### 2.3 理论上限

从 mod 的 `ProgramLimits`（实测常量）：

| 常量 | 值 | 含义 |
|---|---|---|
| `PER_OWNER` | 8 | 每个主人最多 8 个并发程序 |
| `SERVER_WIDE` | 64 | 全服最多 64 个 |

树侧的资源占用很轻：每个同伴一条 lane（一个 tick 定时器 + 一个事件长轮询会话）。

**所以理论上 8 个同伴是安全的，更多会受 `SERVER_WIDE` 与游戏性能限制。**

真正的瓶颈不是树，而是：

1. Minecraft 侧同时跑多个寻路/挖掘的 CPU；
2. 每个同伴一条 `get_events` 长轮询会话（MCP 连接数）；
3. 用户实际能管得过来几个。

**建议实测上限：4 个以内**，再往上要测服务器 TPS。

## 三、发现的问题

| # | 问题 | 影响 | 状态 |
|---|---|---|---|
| 1 | `go_to` 可能长时间不结束（被怪反复打断 / 复杂地形） | 该同伴队列被占住几分钟 | 已有 300 秒调用上限；可考虑按技能设更短的上限 |
| 2 | 求生模式没有食物来源，饿到 4/20 只能反复失败 | 会饿死（mod 会复活） | 需要"觅食/打猎"行为 |
| 3 | 生产模式在无资源群系靠轮换+探索，效率低 | 采集慢 | 可以先扫描再决定，而不是盲试 |
| 4 | 战斗模式未实战验证 | 未知 | 需要夜间/有怪时复测 |
| 5 | 多个同伴共用一条 owner 事件流？ | 未验证 | 每个同伴的 `get_events` 各自独立，应该没问题 |
| 6 | 同伴死亡后树能否自动接管 | 未验证（本次没死） | mod 会复活并换 id，发现循环会刷新 id |
