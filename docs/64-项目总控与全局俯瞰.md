# 64. 项目总控 / 全局俯瞰角色

> 2026-11-10。问题：Lead、行为学家、点子王、产品经理都在“解决当前问题”，围着 bug 打转，丢失大图景。  
> 结论：单独设一个 **项目总控（Project Steward）**，三个专业红队保留；再加持久的大图景文档。

## 1. 为什么不能塞进三个子体

三个子体各自有强偏见：

- 行为学家：行为合理性；
- 点子王：失败/投机；
- 产品经理：范围/验收。

他们是被“当前任务提示”驱动的，冷启动只看本次材料。  
即使加“请从全局看”，也会被本轮问题框住，且没人对跨轮次一致性负责。

需要的是**另一个认知模式**：

```
不是找当前 bug，
而是问：
- 我们现在解决的问题，是不是最重要的问题？
- 当前工作对应哪个能力/里程碑？
- 有没有在用 bug 修补代替能力建设？
- 范围/顺序/债务是否失控？
```

## 2. 角色定义

### 项目总控（Project Steward）

- 风格：冷静、全局、组合思维；不红队、不抠细节、不做验收；
- 只读，不改代码，不调试；
- 不参与日常 bug，只在**阶段门/每日/每周**出现；
- 输入：大图景、当前状态、决策日志、少量证据；
- 输出：一页全局判断 + 优先级/顺序建议 + 风险/债务；
- 权力：建议，不替代 Lead 决策。

### 三个专业红队保留

- 行为学家：行为逻辑；
- 点子王：失败/投机；
- 产品经理：范围/验收。

总控负责“**该不该做/先做什么**”，红队负责“**这样做会不会错**”。

## 3. 持久大图景

必须有一个一页文档，不能只靠聊天记忆：

```text
PROJECT-OVERVIEW.md
  - 北极星
  - 预期能力地图
  - 当前阶段与出门条件
  - 非目标
  - 关键依赖
  - 主要风险/债务
  - 当前正在解决的问题（以及它对应哪个能力）
```

另加：

```text
PROJECT-STATUS.md
  - 当前 milestone / 正在做什么
  - 已完成的 capability
  - 已知 bug（标注：症状修补 / 能力缺口）
  - 下一步 gate

DECISIONS.md
  - 已做决策与理由
  - 防止反复推翻
```

## 4. 总控的调用节奏

- **每天一次**或**阶段门**一次；
- 不按 bug 调用；
- 每次 1 页，最多 10 分钟；
- 输入只给：OVERVIEW + STATUS + 最近决策 + 当前问题；
- 输出固定：

```text
1. 当前工作对应哪个能力？
2. 它是不是当前最该做的？
3. 有没有症状修补/范围漂移？
4. 建议的下一步顺序（≤3）
5. 最大风险/债务
```

## 5. Lead 的工作模式也要改

每次开工前先问三句：

1. 这个任务对应北极星哪个能力/里程碑？
2. 它是在补能力，还是在修症状？
3. 做完后，项目整体向前推进了什么？

如果是纯 bug，记录到 STATUS 的“症状修补”，并定期由总控判断是否该停下来补能力。

## 6. 当前案例

水 bug：

- 直接反应：修 water_stuck/避水；
- 总控视角：这是 `early_survival` 能力缺口（侦察/选址/食物/庇护/路径风险），不是又一个 water fix；
- 所以正确顺序是：先补 early_survival profile/前置回补，再谈两夜。

## 7. 一句话

> **三个红队负责“会不会错”，总控负责“是不是在做对的事”；Lead 用一页大图景约束所有任务，不再被当前 bug 牵着走。**
