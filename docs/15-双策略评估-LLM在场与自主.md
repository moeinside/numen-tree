# 双策略评估：LLM 在场 vs 自主（提案评估，未动工）

> 2026-11-08 04:1x 用户提出。**本文只做评估与设计记录，本轮未改任何代码。**
> 相关：`docs/12` §10.16（方向盘修复，已实现）、§10.17（寻路/施工模块）、`docs/14` 交接。

## 1. 提案原文（用户）

> llm 是否介入，应该给树做两种完全不同的策略：
> 自主长任务，应该是树工具查询 LLM 无反应的时候才运行；有反应的时候，应该就是短的任务组。

## 2. 当前实际是什么（为什么会有"抢方向盘"）

现在是**一套策略里混着两种行为**，靠几个软开关打补丁：

| 机制 | 现状 |
|---|---|
| LLM 目标 | `tree_goal` 默认 priority 20 > 计划步骤 10，排队的目标会优先 |
| 自动行为 | 只在"没有 pending/running 的 mcp 目标" + 20s 宽限期内不启动；但**已经在飞的自动动作不可取消** |
| 动作粒度 | 单动作 30s~240s 不等（`mine_nearby` 240s、`smelt` 240s、`forage` 210s…） |
| 接管预算 | `drive` 300s/20 goals 后自止（防无限），但对自主排障偏短 |
| 自动计划 | 空闲就可能开（feed/gather/bootstrap/patrol），是"树自己的意志" |

结果：LLM 在场时，自动行为仍会和 LLM 抢**唯一执行槽**；且单槽动作最长 240s，LLM 命令只能排队 → 体感"方向盘被抢"。

## 3. 评估：提案对吗？

**方向正确，但表述需要精确化，否则会引入新问题。**

### 3.1 它正确的部分

1. **两种策略应该显式分开**：是否有人类/LLM 在场，直接决定"谁握方向盘、动作能有多长、树能不能自己开计划"，这比现在靠一堆冷却/宽限补丁清晰。
2. **LLM 在场时自动行为不该抢跑**：这正是今天树模式测试失败的三大原因之一（auto bootstrap 在室内派 mine_nearby）。
3. **自主长任务只在无人在场时跑**：符合资源使用（LLM 在场时它应该"待命 + 执行给定任务"，而不是自己逛街）。

### 3.2 但"短的任务组"不能理解成"每步都回来问 LLM"

- 会把之前解决的"雷霆大思考"重新引回来：LLM 每个小步都要醒一次、判断一次。
- 项目边界是"LLM 只下目标，不微操"。正确粒度是：**LLM 一次给一个任务组（tree_task 计划），树在组内自己分步执行；但组内每个动作要短、可抢占（≤20~30s），且组与组之间回到"等 LLM"状态。**

### 3.3 它解决不了的问题（必须配套）

| 问题 | 双策略能否解决 | 说明 |
|---|---|---|
| 自动计划抢方向盘 | ✅ 能 | LLM 在场时禁自动计划 |
| 自动长动作占槽 | ⚠️ 只能缓解 | **在飞动作不可取消**是执行模型硬限制；必须靠"短动作 + 硬上限"才能把等待压到秒级 |
| 无路可走 / 不会施工 | ❌ 不能 | 这是 mod 寻路不会挖/垫，和策略无关 → 需要 `docs/12 §10.17` 的寻路/施工模块 |
| 卡死程序长占槽（move.go 297s） | ⚠️ 部分 | 需要动作级超时 + 超时后清锁（自动动作 60s 已做，LLM 动作还没有） |
| 目标排队被作废 | ✅ 已缓解 | `mcpGoalStaleSeconds=300` + 作废叫醒 |

## 4. 设计草案 v0（记录，不在本轮实现）

### 4.1 状态机

```
attached（LLM 在场）  ──(静默超过 TTL)──▶  autonomous（自主）
        ▲                                      │
        └────(任意 LLM 工具调用 / attach)────────┘
```

- **进入 attached**：LLM 任何工具调用（tree_goal/tree_task/tree_inbox/tree_wait…）立即算"在场"，并刷新心跳；也可显式 `tree_control {op:'attach'}`。
- **进入 autonomous**：LLM 静默超过 `mode.detachTtlSeconds`（建议 180~300s，避免抖动）；或显式 `tree_control {op:'detach'}`。
- 切换时写 trace + inbox 通知（`needsBrain=false`），并在 `tree_status` 摘要里显示 `mode: attached|autonomous`。

### 4.2 两种模式的行为表

| 维度 | attached（LLM 在场） | autonomous（自主） |
|---|---|---|
| 自动计划（feed/gather/bootstrap/patrol） | **全部禁止**（生存只上报 ★，不自己开计划） | 正常开（现行为） |
| 牵引绳 leash | 关闭 / 只报不动 | 启用 |
| 安全中断（near_death/outnumbered/night_danger…） | **仍然生效**（保命永远最高） | 仍然生效 |
| 动作粒度 | **所有动作硬上限 ≤ `interactiveActionSeconds`（建议 20~30s）**，长任务必须分片 | 单动作 ≤ `autoActionTimeoutSeconds`（60s），长任务靠分片累加 |
| 任务组 | 一次 tree_task/一组 tree_goal；组内树自己分步；组间回到"等 LLM" | 树自己决定长时间做什么 |
| drive 自止 | **关闭**（LLM 在场，不需要防失控；有人看着） | 保持（防无限自动） |
| 上报 | 只推 ★ 决策项；完成靠拉 | 只推 ★；完成靠拉 |
| 卡死处理 | 超时 → 清锁（补丁）→ 上报 ★，不自动重试超过 N 次 | 超时 → 清锁 → 按规则重试/换动作 |

### 4.3 需要新增/修改的配置（草案）

```jsonc
"mode": {
  "enabled": true,
  "detachTtlSeconds": 240,        // LLM 静默多久 → 转自主
  "attachOnAnyToolCall": true,
  "interactiveActionSeconds": 25, // attached 下单动作硬上限
  "autonomousActionSeconds": 60   // autonomous 下单动作硬上限（已有 autoActionTimeoutSeconds 可复用）
}
```

### 4.4 与现有机制的关系

- 现有的 20s `autoGraceSeconds` 可以**并入 attached 模式**（attached 期间本来就不开自动计划，宽限期仅用于"刚 detach 前的缓冲"）。
- 现有 `drive` 自止逻辑在 attached 下关闭、autonomous 下保留（或改成 autonomous 的预算）。
- 现在"LLM 到达即放弃 auto 计划"的补丁保留（attached 下更彻底：auto 计划根本不允许启动）。
- `tree_wait` 可以兼作心跳：每次 long-poll 都刷新 attached 心跳。

## 5. 风险 / 未决问题

1. **"无反应"怎么判**：LLM 会话开着但人不在 → 靠 TTL；TTL 太长会浪费机会（饿死前没人管），太短会抖动（LLM 思考/长任务期间被转自主）。建议 TTL 180~300s，并允许显式 attach/detach 覆盖。
2. **attached 下生存兜底**：饥饿/低血时树不能自己开 feed 计划，只能上报 ★ 等 LLM。若 LLM 长时间不响应，要先转 autonomous 再自救（依赖 TTL）。这是有意的取舍：**有人在场时，树不擅自改变主人意图**。
3. **任务组粒度**：tree_task 计划里有 5~10 步，attached 下单动作 25s 上限意味着一个组可能跑几分钟（多次分片）；LLM 中途下新命令怎么办？沿用"新命令到达 → 当前计划让位"（已实现）。
4. **安全边界**：attached 下关闭 leash 可能导致同伴不回家；但这是"LLM 负责"的选择，需在 persona/文档里写明。
5. **对离线测试**：需要新增 fixture：attach→auto 计划不再开；detach TTL→自主计划恢复；attached 动作硬上限（可用假 numen 延迟模拟）。

## 6. 结论与建议顺序

- **采纳这个方向**：把"LLM 在场 / 自主"做成显式双策略，比继续打补丁清晰；但不要把它当"短任务组=每步问 LLM"，粒度应是"组内自跑、动作短、组间等人"。
- **前提条件**（否则双策略也救不了现场）：
  1. 所有动作可中断/有硬上限（目前自动动作 60s，LLM 动作还没有）；
  2. 寻路/施工模块（`docs/12 §10.17`）——今天"no_path 卡死"是它导致的，与策略无关。
- **建议落地顺序**：
  1. 先补"LLM 动作硬上限 + 超时清锁"（小改动，立即见效）；
  2. 再做寻路/施工模块（解决无路可走）；
  3. 最后上双策略状态机（在 1、2 之后，行为才稳定可测）。
- 如果用户希望"立即缓解抢方向盘"，可以先只做 attached/autonomous 的**自动计划开关 + 动作上限**两件事，作为双策略的最小版本。

## 7. 补充提案（2026-11-08 04:2x，用户）：autonomous 模式的目标降级与退避

> 用户补充：no_path 可能只是"自主行动试图回到主人身旁、但主人周围没有可用路径"造成的；attached 模式下 move 是 LLM 给的任务组，所以这个问题会消失；**autonomous 模式下应该改树逻辑：后退一步、换备选任务、放宽目标（主人周围 6 格 / 8 格之类）**。

### 7.1 评估：判断基本正确，但要区分两层

| 判断 | 评估 |
|---|---|
| "回到主人身旁 no_path" 是自主行为自找的 | ✅ 对。牵引绳/守家会自动 `approach_owner(range=4)`；主人站房顶/被围时这个目标不可达 → 反复 no_path，树又不断重试，看起来像"乱跳/卡住" |
| attached 模式下这个问题会消失 | ✅ **前提是 attached 下彻底关闭自主 approach/leash**（见 §4.2）。但注意：**LLM 显式下的 go_to 也可能 no_path**，只是 LLM 能看到失败并自己改目标，不需要树擅自重试 |
| autonomous 模式后退一步、换备选任务、放宽目标 | ✅ 正确方向，且属于"树该有的规则"，不违反"LLM 只下目标"的边界（这是自主策略的一部分） |

**关键区分**：放宽目标（ring 采样）能救"主人站在不可达点"这种**软不可达**；如果同伴自己被困在封闭口袋（今天我们遇到的拆路后情况），放宽到 8/12 格依然 no_path——那是**硬不可达**，必须靠寻路/施工模块（§10.17）或上报，不能无限放宽。

### 7.2 设计草案（autonomous 模式）

1. **目标环带放宽（soft unreachable）**
   - 原目标"距主人 ≤4"失败后，依次尝试环带 `[6, 8, 12, 16]`（只取水平距离最近的**可达**落点；用 `scan.map` 或逐点 `go_to` 探测，逐点试要限次）；
   - 到任一环带内即算"回到主人附近"，不再要求精确贴身；
   - 上限 16 格（别放太宽，否则"看起来没跟上"）。
2. **后退一步再试（backoff）**
   - no_path 连续 2 次后，先 `go_to` 反方向 2~3 格的开口处（或 `retreat`），再重新尝试环带目标；
   - 目的：从"贴墙/死角"挪到有视野的位置，给寻路一点空间；每次 backoff 限 1 次，避免来回抖。
3. **换备选任务（fallback task）**
   - 放宽 + 后退都失败 → 标记"主人附近暂不可达"，**冷却 60~180s 不重试 approach**；
   - 期间转做本地可行任务（`idle`/`eat`/`store_items`/`guard`/`mine` 按配置优先级），每轮只试一次；
   - 冷却后再评估（如果主人移动了、路开了，就恢复）。
4. **上报策略**
   - 同一"不可达"原因 5 分钟内只上报一次（★），避免刷屏；恢复可达时发一条通知。
5. **attached 模式对照**
   - attached 下不自动 approach/leash（LLM 负责）；
   - LLM 显式 `go_to` 失败时，返回里带 hint：`目标精确点不可达，可给 6/8 格范围或换落点`，可选支持 `relaxRange` 参数让技能自己放宽（默认关，由 LLM 决定）。

### 7.3 配置草案

```jsonc
"leash": {
  "fallbackRanges": [6, 8, 12, 16],  // 原 range 失败后的环带
  "backoffBlocks": 3,                 // 连续 no_path 后先退几格
  "unreachableCooldownSeconds": 120,  // 判定不可达后的冷却
  "fallbackTasks": ["idle", "eat", "guard"] // 冷却期备选（按可用性过滤）
}
```

### 7.4 与寻路模块的分工

```
目标不可达
 ├─ 软不可达（主人在房顶/围栏后/窄缝）→ 环带放宽 + backoff → 多半能解决
 ├─ 仍不可达 → 【任务变更】到主人周围某块地方（区域候选点，不必贴身）
 │              └─ 候选全失败（真围死）→ 本地安全点待命 + 冷却 + 上报 ★（只报一次）
 └─ 同伴自己被困（硬不可达，四周无路）→ 寻路/施工模块（挖/垫/搭桥）或上报 ★
```

### 7.5 风险

- 环带放宽可能导致"同伴总在 8~12 格外跟着"，需要上限和"回到主人附近"的明确语义；
- 主人移动中环带点会过期，要每次重新取主人位置；
- backoff 不能把同伴退进更糟的地形（水/岩浆/悬崖）——退避目标要先 `scan` 安全检查；
- 冷却期换备选任务不能与"守家/保命"中断冲突（安全中断仍最高优先级）。

### 7.7 硬不可达时的"任务变更"（用户 2026-11-08 04:3x 澄清）

> 用户澄清：硬不可达的时候，变更任务是——**转换为"到我（主人）周围某块地方"**。即：不是改做无关的活，而是把目标从"精确回到主人身边"改写为"到达主人周围的某个区域/落点"。

**语义**：
- 原任务：`回主人身边（精确点/贴身 ≤4）`
- 变更后：`到主人周围某块地方（区域目标：任一可达的附近落点即可）`

**实现要点（草案）**：
1. **候选点集合**（硬不可达判定后生成）：
   - 环带 `[6, 8, 12, 16]` 上的采样点（按距离升序）；
   - 地点簿里主人附近的命名点（`家`、门口、集合点等，可配置）；
   - 主人站位附近的"最近可达格"（用 `scan.map` / 逐点 `go_to` 探测，限次数）。
2. **选点规则**：先近后远；避开危险（水/岩浆/悬崖/敌对密集）；优先"主人所在区块内"的点；成功定义 = 到达任一候选（**不必贴身**）。
3. **任务记录**：trace + inbox 写明"任务变更：回家 → 到主人附近区域（点 x,y,z）"，让 LLM/主人知道语义变了（attached 模式由 LLM 决定是否接受，自主模式按规则表）。
4. **候选全失败（真围死）** → 任务再变更为"本地安全点待命 + 上报 ★"，不无限重试；后续交给寻路/施工模块（§10.17）或主人处理。

**配置草案**：
```jsonc
"leash": {
  "areaFallback": true,              // 硬不可达 → 区域目标
  "areaCandidateRadius": 16,         // 候选点最大半径
  "areaCandidatePoints": ["家", "门口"], // 地点簿命名点优先
  "areaMaxTries": 4                  // 候选点最多试几个
}
```

**与"放宽 range"的区别**：
- 环带放宽 = 同一目标（回主人身边）只改半径；
- 区域目标 = **任务语义变更**：目标是"主人周围某块地方"，允许落在不同方向/命名点，成功后即视为任务完成（不需要最终贴到主人身边）。
- 两者可叠加：先放宽 range，仍硬不可达 → 升级为区域目标。

**与 attached 模式的关系**：attached 下不自动发起"回家"；若 LLM 明确下 go_to/回家任务失败，树返回 hint 并**建议改用区域目标**（由 LLM 决定），不自作主张。

**风险**：区域目标可能让同伴停在离主人 10~16 格的地方——需要"到达后待命/跟随"的后续语义（到区域后 idle/或等主人移动再重评估），否则会显得"没跟上"。

### 7.6 测试计划（离线 fixture）

1. `owner_on_roof`：owner 在不可直达点，`approach_owner(range=4)` no_path → 环带 6/8 成功 → 不刷屏；
2. `pocket`：四周不可达 → backoff + 环带都失败 → **任务变更**：区域候选（"主人周围某块地方"）也全失败 → 本地待命 + 冷却 + 只上报一次；
3. `attach_no_leash`：attached 下不自动 approach（与 steer_yield 类似）；
4. `relax_backoff_loop_guard`：连续 no_path 不无限重试（次数上限）；
5. `area_target`：硬不可达 → 任务变更为"到主人周围某块地方"，候选点探测选第一个可达点 → 到达即完成，trace 记录"任务变更：回家 → 到主人附近区域(x,y,z)"。

## 8. 设计指导思想提案（2026-11-08 04:4x，用户）：失败降级 / "退一步、换目标" 应成为行为树的核心原则

> 用户：这种行为树上"后退一步、变换目标"的动作，是否应该成为行为树设计的指导思想？

### 8.1 评估：对，建议上升为核心原则 #1（失败降级优先）

**理由**：
1. 现实环境（MC）里"目标不可达/被挡/卡住"是常态而非异常；把失败当异常处理，就会 everywhere 打补丁（我们现在的 `onFail` 分散在配方里、部分还缺失）。
2. 行为树的经典语义本来就是 **Fallback/Selector**（一个不行就试下一个），但我们目前只做到"步骤级 onFail 转移"，缺一个**全局的失败处理策略**：退避 → 放宽 → 换实现 → 换目标 → 上报/待命。
3. 今天所有"卡死/乱跳/饿死"事故本质都是**没有退路**：同一目标无限重试、参数不放宽、换不了任务、也不上报。
4. 这条原则和现有边界不冲突：LLM 仍持有"目标/否决/时间"权；树负责"怎么在规则内找退路"。**退路也必须由规则表决定，而不是代码里临时 if。**

### 8.2 形式化：两层落地（数据驱动，不是新骨架）

**第一层：目标契约（goal contract）**——每个目标/配方步骤声明：
- `successWhen`：成功判定（如"到达任一可接受点"）；
- `acceptableVariants`：可接受的降级变体（range/area/备选落点/备选材料）；
- `maxRetries` / `deadline`：重试上限与时限；
- `fallbackGoal`：本目标做不成时改做什么（如 approach → 区域目标 → 待命）；
- `giveUpAction`：彻底失败时（上报 ★ / 本地待命 / 转施工）；
- `ownerIntentInvariant`：**不可违反的意图约束**（如"回家"≠"离家更远"）。

**第二层：失败降级阶梯（failure ladder）**——统一顺序，避免每个技能自己发明：
```
1. 重试（同参数，限 1~2 次）
2. 放宽参数（range→环带；精确点→区域；数量/时长变小）
3. 换实现（不同技能/不同路径/先施工再走）
4. 换目标（备选任务；见 §7.7 区域目标）
5. 上报 ★ + 本地待命/冷却（只报一次）
6. 冷却后再评估（主人移动/路开了/环境变了）
```
每一级都要**有预算**（次数/秒数）和**安全检查**（后退不能退进危险区）。
每一级变更都必须写 trace/inbox（"任务变更：X → Y，原因 no_path"），便于 LLM 审计。

**第三层（可选）：配置化"退路表"**
- 新增数据文件（如 `src/recovery.mjs`）：`{skill, failKind} → 降级动作序列`；
- 与现有 `onFail` 的关系：`onFail` 是**配方内显式转移**，`recovery` 是**未声明时的全局兜底**；显式优先于全局。
- 这样新增技能/配方不用每次手写 onFail，也不会再出现"某个失败 kind 没接住 → 卡住"。

### 8.3 权限边界（防止"树擅自降低要求"）

| 模式 | 谁决定"可接受到什么程度" |
|---|---|
| attached（LLM 在场） | **LLM 决定**：树只能执行 LLM 声明的 `acceptableVariants`，或失败后给 hint/★ 让 LLM 改目标；树不擅自换目标 |
| autonomous（无 LLM） | **规则表决定**：在预设的 acceptableVariants/recovery 表内自由降级，超出则上报/待命 |

原则：**降级只能在"声明的可接受集合"内进行**；越界必须上报，不能悄悄把"回家"降级成"在附近晃"。

### 8.4 度量与验证（否则原则无法证明有效）

- 指标：目标失败率、降级成功率（第几级救回来）、上报率、重复 no_path 次数、平均动作时长、卡死动作数；
- 测试：每个技能至少 2 个失败 fixture（no_path / out_of_reach / timeout），断言"按阶梯降级、有预算、最终有明确结果（成功/上报）"；
- 回归：不允许出现"同一失败无限重试"（可在回放里断言 action 次数上限）。

### 8.5 结论

- **建议把"失败降级 / 退一步换目标"写进行为树设计原则第 1 条**（在"边界（LLM 只下目标）"之后），并作为新技能/配方的准入要求：**没有失败降级路径的技能不允许上线**。
- 实施顺序不变：① 动作硬上限 → ② 目标降级/区域目标（§7） → ③ 寻路/施工模块 → ④ 双策略状态机；其中 ② 本身就实现了原则的一半，建议先做。
- 与"行为树经典 Fallback"的关系：我们是"规则+配方"的树，不需要引入完整 BT 节点库；把 Fallback 语义**下沉到目标契约 + 降级阶梯数据表**即可，不破坏现有架构。
