# 96. 测试前置：numen 权限模式（完全控制权）

> 2026-11-10。回答“玩家完全离线时，同伴动作被审批卡住”的问题。  
> 结论：测试员没有绕开审批；要完全控制权，需在测试前设置 `permission mode=bypass`。

## 1. 实际机制

numen 的权限层是 `permission.Gate`，每同伴有一个模式：

```text
ASK     默认；需要 owner 同意的动作会弹 consent（owner 建筑/容器/危险改动）
BYPASS  全部允许；不再询问 owner
OBSERVE 全部拒绝写操作（只读观察）
```

模式持久化在世界的 `PermissionStore`，不是每次临时问。

## 2. Day1 测试员那次到底发生了什么

日志明确：

```text
numen.work.dig: denied
did not dig 125,71,181: refused by the owner:
主人不在场,无法征得同意
(asked: break 1 oak_log ...: placed by a player)
```

- 这是 **玩家放置的方块** 触发的 owner consent；
- 测试员**没有绕过**，它改为砍自然树（wild logs）；
- 它随后成功放置工作台/熔炉、合成、进食，所以“摆方块”不是全部都要审批；
- 审批只针对 owner 建筑/容器等敏感对象。

## 3. 完全控制权的设置方式

测试前，owner 在游戏内执行一次：

```text
/numen permission mode bigwhale bypass
```

检查（owner 在线时）：

```text
/numen permission mode bigwhale
```

然后 owner 可以离开 MC 窗口。模式已持久化，测试期间不再需要 UI 审批。

恢复默认：

```text
/numen permission mode bigwhale ask
```

## 4. 测试口径

- `bypass` 是 **numen 的游戏权限配置**，不是 GM/作弊通道；
- 但它改变了测试前提，必须在 manifest 记录：

```json
{ "permissionMode": "bypass", "ownerPresentAtSetup": true }
```

- `permissionMode=bypass` 的 run 不能和 `ask` 的 run 直接比较；
- `bypass` 允许触碰 owner 建筑/容器，测试世界必须可回滚；
- 若目标是“玩家离线时默认行为”，保留 `ask`，并接受相应拒绝；不要把拒绝当树的能力失败。

## 5. 如果 owner 连设置时都不能在线

需要开发侧提供 setup 路径（另开审批），例如：

- GM 通道允许执行 `numen permission mode ...`（需加白名单，且仅 setup 时）；
- 或专门的 dev setup 命令；
- 不建议直接改世界 `PermissionStore` NBT。

## 6. 一句话

> **测试员没有绕开审批；要完全控制权，就在测试前把该同伴的 `permission mode` 设为 `bypass`，并把这一前提写进 manifest。**
