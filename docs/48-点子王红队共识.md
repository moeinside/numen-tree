# 48. 点子王红队共识：可开工的最小方案

> 2026-11-10。三轮红队讨论（R1 攻击 → R2 实际细节反驳 → R3 最终共识）。  
> 角色：点子王（悲观投机架构师，不了解项目实现细节）。  
> 结论：**有条件同意，值得开工。**

## 1. 最终共识

1. **不承诺“多日任务必达”**；目标改为：
   - milestone 进度单调推进；
   - 死亡有界；
   - 失败有界。
2. **单种子不能证明架构**；验收用：
   - 固定种子；
   - ≥3 个未参与调参的留出种子；
   - 扰动（挪箱/拆床/丢物品）；
   - 结论只写“留出种子上可泛化”。
3. **不写通用 HTN / Planner**：
   - SOP 队列 + 仅补缺失前置的有界回推；
   - depth ≤2、节点上限。
4. **不做多 profile 并发 / aging 抢占**：
   - 单活跃 milestone；
   - profile 只存 progress/lastProgressDay。
5. **Claims 完整账本砍掉**：
   - 只保留单条 reservation（owner milestone + 到期释放）；
   - 到期绑游戏内日界，进程重启一律作废重建。
6. **SiteRegistry 保留但只做候选索引**：
   - 箱/水/工具/站点使用前现场校验；
   - lastVerified 不是权威。
7. **先修 resume bug**：
   - blocked 计入；
   - 恢复前成功观测门槛；
   - 同因重试 ≤3；
   - suspend→resume 抖动计数。
8. **全局失败预算 + 降级**到存活/修补模式，不是无限局部冷却。
9. **milestone 落盘，不存 plan cursor**；
   - 单 profile + milestone 列表的最小 DurableGoalStore；
   - 多 profile 不阻塞两夜验收。
10. **死亡后从最近 milestone 边界续跑**，Readiness 重补装备。

## 2. 最后一条硬约束（点子王的条件）

持久化必须定义：

1. **原子写**：单文件 + 版本/校验，写坏回退上一 milestone；
2. **重启幂等**：进入 milestone 不重放已完成副作用；
   - 进入前 use-time revalidate；
   - 已完成步骤靠世界观测判定（“炉里已有铁”而不是“我执行过烧铁”）；
3. 验收增加：**replay 副作用次数 = 0**。

## 3. 最小落地顺序

### P0

1. 修 resume 抖动（blocked/观测门/重试上限/指标）；
2. Facts 新鲜度 + use-time validation；
3. 全局失败预算 + 降级；
4. 最小 DurableGoalStore（原子写、幂等、单 profile + milestone）；
5. 无 LLM 两夜闭环。

### P1

6. SOP + 有界方法回推（depth≤2）；
7. SiteRegistry + 单条 reservation（游戏日界到期、重启作废）；
8. 死亡后 milestone 续跑 + Readiness 重补装备。

## 4. 两夜验收

固定种子、无 LLM、玩家零干预：

- 每夜至少完成 1 milestone，进度单调；
- suspension 占任务时长 <20%；
- 无状态不变的 suspend→resume 循环 >2 次；
- 同因重试 ≤3；
- 无“忙而无进度”>90s；
- death ≤1，且死亡后从最后 milestone 继续；
- 日中 kill 重启后续跑同一 milestone；
- 夜间室外任务 = 0；
- replay 副作用次数 = 0。

防脚本：≥3 个留出种子 + 一次扰动；结论写“可泛化”，不写“架构正确”。

## 5. 一句话

> **先修 resume 抖动与验证门，再落最小 DurableGoalStore；单 profile + SOP + 有界补缺 + use-time validation 已足够开工，多 profile/账本/通用 Planner 都后置。**
