# 137. 圆桌：滑动执行树 vs 优先度打分隔离

> 2026-11-12。点子王 × 总控 × 行为学家 × MC 专家 × 项目经理。  
> 用户期望：滑动树决策快；原子动作执行时间可以阻塞，但不能拖慢决策。

## 1. 结论

```text
要隔离，但不是两个调度器。
隔离“打分/候选”与“承诺/执行”。
决策永不等待执行 I/O。
单写者：滑动树/执行器是唯一承诺写入者。
```

```text
打分 = 值不值得（候选、理由、有效期）
滑动树 = 现在做不做、何时退（承诺、放弃、下滑）
执行器 = 独占动作槽、原子边界、postcheck
```

## 2. 打分交付给滑动树什么

最小契约：

```text
decisionInput {
  snapshotSeq, gameTick,
  candidates: [{ id, priority, consequence, reversal, eligible, evidence, validUntil }],
  hardSignals: [],
  staleFields: []
}
```

规则：

```text
只读、不可变
硬信号事件驱动
软分按段边界/N tick 更新，不每 tick 重建
字段级 TTL + validUntil
过期候选不可选
树不重算分、不反写打分
```

## 3. 决策快 + 原子阻塞的并发模型

```text
decision：纯函数，读快照，不 await，不写 state
execution：独占 actionLock + cursor + tx + postcheck + 失败计数
通信：单向 intent 队列 + 只读快照
```

五条硬边界：

```text
1. 决策永不等执行；执行永不等决策
2. actionLock 只能执行器申请/释放
3. 执行期间决策照常跑，但不能改当前 cursor
4. 观测/postcheck 只由执行器/观测器写
5. 决策节拍与执行耗时解耦
```

动作阻塞时：

```text
树可以预备下一步（prefetch）
但不能改写当前动作
新决策在原子边界提交
```

## 4. 冲突裁决

```text
硬安全/反射 > 已提交承诺 > 软分候选
```

两个来源不能都当权威；否则双写/抖动。

## 5. 落地顺序（总控）

```text
1. 影子期：滑动树只读，与打分器同批真实 run 逐拍对照
2. 窄缝接管：只接管 承诺/放弃/失败下滑
3. 层级接管：A1 排班 + A2 领域层
```

每段设门，不可跳。

## 6. 验收指标（PM）

决策侧：

```text
决策延迟 p50/p95/max
最大决策间隔
replan 延迟 p95
长原子期间每分钟决策数
排队年龄
```

执行侧：

```text
原子时长 p95/max
超预算原子数
槽占用时长
硬信号→边界处理延迟
```

硬门槛：

```text
p95 决策延迟 ≤ 200ms
最大决策间隔 < 1s
60s 长原子期间决策不停
actionLock 持有期间 decision_tick 间隔 ≤ 2× 目标节拍
```

判负：

```text
决策等动作返回而阻塞
同一原子基于两个 snapshotSeq 重复下发且无 in-flight 去重
玩家可见状态与实际 actionLock/atom 不一致
用均值/剔除阻塞窗口宣称决策快
```

## 7. 不隔离的替代

```text
不隔离 = 必须原子段化
单次原子阻塞 ≤2s
长动作拆成原子段串行
“动作本来就要跑很久”不能解释决策卡顿
```

## 8. 两个最大风险

```text
1. 快照新鲜度错位：决策基于 T，结果 T+N 才回
   → in-flight 账本 + snapshotSeq 去重

2. 两套优先级打架
   → 硬安全 > 承诺 > 软分；单写者
```

## 9. 一句话

```text
决策快 = 决策线程永不等待执行 I/O；
不是把重排塞进每一拍。
手可以慢，眼和脑不能等手。
```
