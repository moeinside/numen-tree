# 全功能树设计（M1 骨架）

> 目标：把树从"一次一个技能的单步执行器"改成"意图 → 计划 → 分步执行 → 阶段上报"。
> 边界不变：树只做**查表 + 固定规则**，不做价值判断；LLM 只有目标/否决/时间权。
> 本文是 M1 的实现依据；验收在 §8，改动波及在 §1.3。

---

## 1. 三层分离

| 层 | 文件 | 变化频率 | 谁改 |
|---|---|---|---|
| **骨架** | `daemon.mjs` `lane.mjs` `plan.mjs` `state.mjs` | 极低（M1 之后基本不动） | Lead |
| **契约** | `skills/*.mjs`（id/params/build） | 低（加新技能卡时才动） | Lead/队友 |
| **数据** | `recipes.mjs`（配方）`interrupts.mjs`（中断表）`places.json` `world.json` `tree.config.json` | **高（加功能就动这里）** | 任何人，只加数据 |

### 1.1 三种"什么时候做什么"

| 类型 | 放哪 | 回答的问题 | 加新行为的方式 |
|---|---|---|---|
| 中断/抢占 | `interrupts.mjs` | 正在干活时遇敌/低血/天黑/卡住怎么办 | 表里加一行 |
| 计划内转移 | `recipes.mjs` 的 `next`/`onFail` | 到地方了做什么 / 这步失败了走哪 | 改 label 字符串 |
| 事件反应 | `lane.mjs` 的事件表（死亡/主人说话/被打/task_finished） | 世界事件来了怎么反应 | 加一个分支（少量代码） |

### 1.2 一句话规则

- **安全中断不许写进配方**；**配方里不许写"血低就撤"**。
- 加一条完整任务 = 加一条配方；加一个原子动作 = 加一张技能卡；加一个反应 = 加一行中断表。
- 核心代码里不许出现具体行为（"遇敌怎么办"必须从表里读）。

### 1.3 改动波及表（以后判断需求范围用）

| 需求类型 | 骨架 | 技能卡 | 配方/数据 |
|---|---|---|---|
| 调行为/优先级 | — | — | 1 行 |
| 组合已有能力的新任务 | — | — | 1 条配方 |
| 新的原子动作 | — | 1 张新卡 | 配方引用 |
| 需要新信息 | 观测加字段 | — | 可选字段 |
| 新的 MCP 入口 | — | — | mcpserver 一个工具 |
| 步内中断（跑一半也要能停） | lane 改 | 4 张长卡改分段 | — |
| 换执行模型/换语言 | 全部改 | 全部改 | 全部改（不做） |

## 2. 数据形态

### 2.1 Plan / Step

```js
plan = {
  id: 'pl3', recipeId: 'stock_wood', intent: '把木头存了', source: 'llm', // llm|auto|interrupt
  status: 'active',            // active|suspended|done|failed|abandoned
  cursor: 'home',              // 当前步骤的 as
  visits: { chop: 1, home: 1 },// 每个步骤访问次数（防循环）
  suspendedBy: null,           // 抢占它的中断 id
  startedAt, stepResults: []
}
step = {
  as: 'home',                  // 标签（转移目标）
  skill: 'go_to' | null,       // 技能步
  type: null | 'report' | 'halt', // 非技能步
  params: { place: '家' },     // params 里可以用 place 名字，lane 负责解析
  next: 'store',               // 成功后的下一步；null = 计划完成
  onFail: { not_found: 'craft_chest', no_path: 'report' }, // 失败 kind → 标签
  maxVisits: 2,                // 同一标签最多进入几次
  budgetMs: 60000              // 可选：覆盖技能的默认预算
}
```

### 2.2 配方（`recipes.mjs`）

```js
{
  id: 'stock_wood', title: '砍木头存箱子',
  match: ['把木头存了','存木头','木材入库','stock wood'],   // 意图别名（模糊匹配）
  steps: [ ... ]
}
```

### 2.3 中断（`interrupts.mjs`）

```js
{
  id: 'near_death', priority: 90, cooldownSeconds: 20,
  when: (st, cfg) => st.hp != null && st.hp / 20 <= 0.4 && (st.hostileCount ?? 0) > 0,
  goal: { skill: 'retreat', params: { distance: 16 } },   // 或 { type:'halt', escalate:'stuck' }
  resume: 'resume'   // resume|restart|abandon（中断结束后怎么对待被抢占的计划）
}
```

## 3. 执行流程（每 tick）

```
① 观测（有节流）
② 事件循环（独立会话，随时更新状态）
③ 中断检查：#interrupts 依次求值（带冷却）。命中 →
     - 当前计划 status=suspended（记 suspendedBy）
     - 推送中断目标（note: 'interrupt:<id>'）→ 走普通执行
     - 中断结束后按 resume 处理：resume 继续 / restart 重来 / abandon 作废并上报
④ 若当前计划 active：取当前步骤 → 执行（一次技能 lua）→ 看结果 → 按 next/onFail 转移
     - 步骤成功：trace + 可选阶段通知（不叫醒大脑）
     - 步骤失败：查恢复表 → 转标签 / 重试（maxVisits） / 上报失败
     - 计划完成：上报 plan_done（LLM 计划叫醒；auto 计划只通知）
⑤ 没有计划：走原有自动规则表（求生/模式）→ 产出的可以是
     - 单个技能目标（as now）
     - 自动计划：feed（觅食闭环）/ go_home（夜间守家）
⑥ 牵引绳 / 待命
```

### 3.1 恢复表（失败 kind → 默认处置）

| kind | 默认处置 |
|---|---|
| `not_found` | 按配方 `onFail` 走替代步骤；没有就换配方 / 上报 |
| `no_path` | 先重试 1 次 → 仍失败：放弃该步并上报 `plan_failed` |
| `slot_blocked` | 降频观测，计划挂起（suspended），不重派 |
| `timeout` | 先观测，确认槽空再重试；不重发同一动作 |
| 其它/unknown | 重试 1 次 → 上报 `plan_failed`（带 step 与结果事实） |

### 3.2 报告预算（2026-11-07 23:4x 已按此实现）

原则（边界 #7）：**完成/通知靠拉，求助才推。**

| 事件 | trace | 通知（needsBrain=false，可拉） | 叫醒大脑 |
|---|---|---|---|
| 自动行为 / 中断 / 牵引绳 完成 | ✅ | —（不进收件箱） | — |
| LLM 单技能完成 `goal_done` | ✅ | ✅ | — |
| LLM 计划完成 `plan_done` | ✅ | ✅ | — |
| 计划阶段完成 `plan_stage` | ✅ | ✅ | — |
| 计划失败 `plan_failed` | ✅ | — | ✅（仅 LLM 来源；auto 只通知） |
| LLM 目标超时作废 `goal_expired` | ✅ | ✅ | — |
| 求助（starving/stuck/death/slot_blocked/drive_stopped） | ✅ | — | ✅ 原样 |
| `auto_action_failing` | ✅ | 窗口内重复 → 通知 | 首次 ✅ |
| 同类求助静默窗口 | ✅ | 窗口内重复 → 通知 | 窗口外 ✅（`escalateDedupeSeconds`，默认 300s） |

实测效果：改完后一次小会话收件箱 5 条里只有 1 条 `needsBrain`（改之前几乎每条都唤醒）。

## 4. M1 配方（三条）

### 4.1 `feed`（觅食闭环，auto）

```
eat  --not_found-->  forage  --not_found-->  seek_food  --(走完一轮)-->  eat (maxVisits 3)
                                                                    └──> report(starving) （饿了且连续 3 轮没吃到）
```

### 4.2 `go_home`（夜间/危险守家，auto 或 llm）

```
go_to(place=家)  --ok-->  hold（idle 短等待 + 重新评估）
                 --not_found(没记家)--> report(no_home) → 退回"守住主人"（go_to owner）
```

### 4.3 `stock_wood`（砍木头存箱，llm）

```
dig_nearby(oak_log,8) --not_found--> explore(20s) --(visited<2)--> dig_nearby
                       --ok--> go_to(place=家) --ok--> store_items(oak_log)
                               └ not_found--> report(no_home)
store_items --not_found(没箱子)--> craft(chest) --> store_items
```

## 6. 接口变更

### 6.1 MCP 工具

- 新增 `tree_task`：`{ companion, intent, constraints?, deadline_seconds?, params? }`
  - 成功：`{ok:true, plan:{id, recipeId, title, steps}}`

### 10.7 LLM 接管自止（2026-11-07 23:1x）

问题：LLM 接管后会连续自动操作，没有停下来的机制（用户实测）。
机制（`tree.config.json` 的 `drive` 段）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `drive.maxSeconds` | 150 | 一次接管最多连续操作这么久 |
| `drive.maxGoals` | 10 | 一次接管最多执行这么多个 LLM 目标 |
| `drive.idleStopSeconds` | 60 | 这么久没有新 LLM 指令 = 接管结束，回自动模式 |

- 每次 `tree_goal` / `tree_task` 刷新接管窗口；`tree_status.drive` 显示已跑秒数/目标数/是否已自止；
- 超预算 → **自动暂停 + 取消所有待执行 LLM 目标 + 中止 LLM 计划 + 上报 `drive_stopped`（needsBrain）**；
- 恢复：`tree_control resume`（重置预算）或 `tree_task` 重新下任务（新任务重置预算）；
- 自止状态下 `tree_goal` 会被拒绝（reason=`drive_stopped`），必须显式恢复。

### 10.8 放置能力（2026-11-07 23:1x）

| 技能 | 参数 | 说明 |
|---|---|---|
| `place_block` | `item, where:"beside"|{x,y,z}` | 脚边找"空气+下方有支撑"的格子放一块；校验背包数量 |
| `place_build` | `item, shape:"line"|"wall"|"cells", anchor, direction, length, height, maxBlocks≤build.maxBlocks, cells` | 一排/一面墙/指定格子；一次 `numen.build.place(cells)` 放一批，不撞 200 调用上限 |

- 放哪里/什么时候放仍归配方或大脑；技能只做"把方块放到给定/脚边格子"。

### 10.6 今晚新确认的坑（已同步 docs/10 第 12 节）
- **ESM 热重载坑**：`reloadSkills()` 必须给模块 URL 加 `?t=` 破缓存，否则热重载拿回旧模块（实测：改了 place_block 却还报旧文案）。已修。
- **`numen.build.place` 不替换占位方块**：雪层/木板这类"非实心但占位"的格子会 `out_of_reach`；`beside` 锚点改为"列一批空气候选，逐个试到成功为止"。

### 10.12 僵尸锁外部清理（补丁 v3 + 树工具，2026-11-08 01:2x）

**问题**：numen 的 `ServerPrograms.RUNNING` 是 JVM 静态表，程序没正常结束（切档/客户端死在调用途中/死亡打断在途调用）就把同伴 UUID 永久留在表里，之后 lua 一律被拒：`a program is already running...`。旧 SOP 要 `delete_companion`+`create_companion` 重建，**掉背包、id 变、要停树重启**，太影响实机。

**为什么 v2 补丁没生效**：v2（启动清/死亡定向清/`/numenlockfix`）用的反射 `com.dwinovo.numen.program.ServerPrograms.RUNNING`；实测 00:15 两个同伴死亡时**日志里一条 `[numenlockfix]` 都没有**，锁一直留到手动重建。v3 因此把"反射是否找到类 / 每次事件清了几个"全部打成显式日志，并加多重类加载器兜底，便于一次定位。

**补丁 v3（`patcher/`，modId numenlockfix 1.1.0）**：
| 能力 | 说明 |
|---|---|
| 本地控制端口 | `127.0.0.1:8768`（只绑回环）：`GET /status` 看补丁版本/反射是否成功/当前锁条目；`POST /unlock?uuid=<同伴UUID>` 清一个；`POST /unlock?all=1` 清全部 |
| 清锁方式 | 走 numen 公开 API `ServerPrograms.cutOff(uuid, programId, false)`（内部 `Program.cancel`）后再删表项；比只删 Map 干净 |
| 显式日志 | 加载/启动/死亡/手动/HTTP 每次清锁都打 `[numenlockfix] ...`；找不到类会打 loader 尝试链 |
| 原有兜底 | 服务器启动清空、同伴死亡定向清、`/numenlockfix`（权限 2）保留 |

**树侧（`src/lockfix.mjs` + `lane.mjs`）**：
- `behavior.lockRecovery`（`tree.config.json`）：`enabled/port(8768)/unlockAfterBlocked(2)/minIntervalSeconds(30)/timeoutMs`；
- **自动**：慢观测连续被拒达到 `unlockAfterBlocked`（默认 **2 次**）→ 调补丁 `POST /unlock?uuid=同伴id`；成功则清零 `slotBlocked`、立刻重观测、发一条 `lock_unlock` 通知（`needsBrain=false`，不叫醒）；失败则退回原来的"第 3 次上报 / 持久化建议"路径；
- **手动工具**：CLI `node src/cli.mjs lock [--companion 名|--all]`、控制 API `GET/POST /lock`、MCP `tree_control {op:"unlock"|"lock_status"}`；
- 补丁没装/游戏没重启时优雅降级（`ok:false`），不会每 tick 重试（有 30s 间隔）。

**验证**：
- `probe/lockfix-selftest.mjs`：**13/13**（起本地假补丁 HTTP 服务，验证 status/unlock uuid/unlock all/参数校验/补丁不在线降级）；
- 回放新增 `lock_recover`：连续 2 次 blocked → 假补丁清锁 1 次、`slotBlocked` 归零、`lock_unlock` 不叫醒、不走到第 3 次求助（回放总数 **11 场景 / 112 断言全过**）；
- 实机（2026-11-08 01:18 重启游戏后）：补丁日志确认加载 `Numen Lock Fix 1.1.0`；`GET http://127.0.0.1:8768/status` → `{patch:"1.1.0", foundClass:true, count:0}`（**反射确实找到了 `ServerPrograms`**，v2 的静默问题已解决）；
- 树侧实机：`node src/cli.mjs lock` → patch 1.1.0 / foundClass true / 同伴 `slotBlocked:0`；`lock --companion bigWhale` → `{ok:true, cleared:0, noop:true}`（没有锁时是 noop 不是错误）；`lock --all` 同样通。
- **端到端验收（2026-11-08 01:24，故意造锁）**：在 `explore` 正在跑时强杀树进程 → 补丁 `/status` 立刻看到 `count:1, program:"ext-222"`（orphan 程序）→ 起新树 → 慢观测连续被拒 2 次 → `17:25:36 lock_unlock 自动清锁成功 cleared=1（未重建同伴）` → 同伴动作/计划自动恢复，**id 与背包不变**。这是 v3 的核心链路，已实证。
- **`/status.count` 语义注意**：`count` 是"当前在跑的程序数"，**不是锁数**——空闲=0、正常动作中=1 都正常；僵尸锁的表现是"count=1 但树被连续拒绝"。自动清锁只在 `slot_blocked` 时触发，不会误杀正常动作（手动 `lock --all` 会 cancel 当前程序，慎用）。

**注意（补丁日志可见性）**：补丁用 `System.out.println` 打的 `[numenlockfix]` 行**不会进 latest.log**（这套启动方式的内置服务器 stdout 没被 log4j 文件 appender 收），所以诊断请以 `GET /status` 为准，不要因为没有日志就判定补丁没生效。

**限制/注意**：mod 只在 JVM 启动加载 → 换 jar 必须重启游戏一次（之后再加锁都不用重启）；**游戏重启后树进程也必须重启**（旧树的 numen MCP 会话会失效，表现为 `this tool needs a 'companion' argument` / `fetch failed`，2026-11-08 01:16 已实证）；补丁不可用时仍按原 SOP（重建同伴/`/numenlockfix`）兜底。

### 10.15 MCP 回报精简：别再让"看状态"变成大思考（2026-11-08 02:5x）

**现象（用户观察）**：直连 numen MCP 时每步结果几百字节，思考很短；换成树 MCP 后每步像"雷霆大思考"。

**定位**：`tree_status` 默认返回**完整 JSON（实测 17KB+）**：每个同伴的 inventory、progress、完整 goals（含 params/lastResult）、plan、drive……LLM 每看一次状态就吃十几 KB，而且状态里大部分信息是树自己内部用的。

**修法（纯展示层，不改数据/决策）**：
| 工具 | 默认（精简） | 开关 |
|---|---|---|
| `tree_status` | **每同伴一行 summary**（位置/HP/饥饿/任务/队列/计划/上一步）+ 收件箱待决策数：实测 **210B** | `detail:true` → 原完整 JSON（同场合同口径 3.1KB，忙时可达十几 KB） |
| `tree_inbox` | 每条压成一行短文本（message 优先；计划/步骤类给 `recipe/step ok→next`）：实测 **196B** | `full:true` → 带原始 detail JSON；`limit` 默认 30 |
| `tree_wait` | 已经只返回 needsBrain 条目 + 每同伴一行 summary（维持） | — |

**原则**：树掌握节拍，LLM 只看"分类 + 事实 + 需要决策的"；完整内部状态只在排障时用 `detail/full` 拉，不进日常上下文。

**验证**：`tree_status` 17,236B → **210B（约 82× 缩小）**；`tree_inbox` 同批 550B → 196B；树功能不受影响（回放 14/14、137 断言仍全过）。

### 10.16 方向盘（steering）：LLM 接管 vs 自动行为的冲突修复（2026-11-08 19:2x~19:4x）

**背景**：树模式会话实测"削平室内 0/30 格"——不是能力不够，而是**唯一执行槽被自动计划的长动作占住**：
`bootstrap_kit` 在室内派 `mine_nearby` → 游戏内 `numen.move.go` 卡死 297s → 树干等 255s → 之后全部 slot_blocked；
12 分钟里约 9 分钟被一个卡死动作吃掉；两次 LLM 指令之间的空隙自动计划又会立刻抢回方向盘；`goalStale 120s` 还会静默丢掉排队的 LLM 目标。

**修复（骨架层，不破坏边界）**：
| 机制 | 配置键 | 行为 |
|---|---|---|
| **LLM 接管即让位** | — | `tree_goal/tree_task` 到达时：正在跑的 `source=auto` 计划直接 **ABANDONED**（不等它跑完）；排队中的 `auto:` 目标取消；LLM 计划可抢占 auto 计划（不再返回 busy 卡住） |
| **接管宽限期** | `drive.autoGraceSeconds=20` | LLM 最近活动后 20s 内，仲裁/牵引绳/待命都不抢方向盘；每条 LLM 指令续期 |
| **自动动作硬上限** | `loop.autoActionTimeoutSeconds=60` | **自动行为**（auto 计划步骤/auto 单目标）的在途 Lua 限时 60s（LLM 自己的目标保持原预算）：卡死动作更快进入"槽位被占→lockfix 清锁"路径，LLM 最多等 ~65s |
| **排队目标不静默丢** | `loop.mcpGoalStaleSeconds=300` | LLM 目标排队上限 120s→300s，且作废时 `needsBrain=true`（明确叫醒） |
| **接管预算放宽** | `drive.maxSeconds=300 / maxGoals=20` | 自主排障不被 150s/10 目标过早自止（仍有限，防无限跑） |
| **可见性** | — | `tree_status` 摘要会写"其中 LLM 目标 N 个在等当前动作（会先跑完手上这个）" |

**回归**：回放新增 `steer_yield`（自动计划跑到一半 → LLM 接管 → auto 计划 abandoned、auto 队列清空、宽限期内不开新 auto 计划）；回放 **15/15、144/144 断言全过**。

**救援记录**：树模式报告后，bigWhale 卡在 (-161,63,177) HP0.8/饥饿5，按 SOP 重建（新 id `0eb125d9…`，HP20/饥饿20，召回到主人身边）。室内削平改为"不再硬挖 30 格"——**只需在被地形占住的 6 个空格 y=64 补木板**即可得到完整平面（其他 30 格本来就有 y64 地形块），比逐格挖安全得多；待同伴进屋/被 tp 后执行。

### 10.17 专用寻路/施工模块（用户 2026-11-08 提出，下阶段做；也见 §11 想法池）

**背景**：mod 自带的 route/path 只会走"现成的可通行格"，**不会挖通/垫路**。实测：
- 用户为了防怪把通往房顶/上下的路拆掉后，同伴被围在无路可走的口袋里 → `go_to` 全 `no_path`；
- 连半径 24 内的掉落物都 `collect` 不动（`no way to the ...`）；
- 树只能眼看着它原地"乱跳"、最后饿死/卡死。

**设计草案（数据 + 少量技能卡，仍守边界：规则在表里、动作在卡里）**：
- 触发：`go_to/approach_owner/collect` 返回 `no_path` 时，由计划层/仲裁层启动"施工模式"（不是改 mod 寻路）。
- 能力拆成原子技能（每段短、可被中断抢占）：
  1. `dig_step`：挖前方 1~2 格高差/挡路方块（带黑名单：不挖脚下承重、不挖岩浆/水相邻）；
  2. `place_step`：在前方/脚下垫一块（上 1 格台阶 / 填 1 格沟 / 搭桥）；
  3. `dig_tunnel`：水平挖 1×2 通道 N 格（分段、每段回仲裁）；
  4. `pillar_up`：原地垫柱上升（放脚下块→跳），用于出坑/上房顶；
  5. `ladder_down/up`：若有梯子/脚手架优先用，没有则垫/挖。
- 路径决策放数据层：失败 kind（no_path / out_of_reach / 目标在上/下/同层/有水/有墙）→ 施工动作表；先尝试 1 格台阶/1 格沟等最便宜动作，逐步升级。
- 状态：施工进度（已修几段/离目标还差多少）沿用分片 partial+remaining；每段之间照常跑中断检查（血低/遇敌先撤）。
- 验证：离线 fixture（no_path → 施工序列 → 到达）+ 实机"拆掉路再让它回家"。

### 11.1 素材/食物类任务完成后的冷却期

用户想法：*采集回来放箱子里、出去打猎回来烤肉放箱子里* 这类任务完成后，应该进入一个**冷却期**，除非 LLM 明确指示继续相关工作。

设计草案（M2/M3 再做）：
- 配方完成时写一个"任务冷却"记号（按 `recipe + companion` 记 `lastDoneAt`），冷却期内自动仲裁**不再开同类计划**（比如 10 分钟不主动砍木/烤肉）。
- 冷却期只挡"自动开计划"，不挡 LLM 显式 `tree_task`/`tree_goal`；LLM 指示 = 显式解除。
- 冷却参数放 `tree.config.json`（例如 `behavior.recipeCooldowns: { stock_wood: 600, cook_meat: 900 }`），默认给几个常识值。
- 好处：避免"箱子已经存满还一直砍树/烤肉"的无意义循环，也减少唤醒。

### 11.2 无 LLM 驱动时的默认装备/工具兜底（尤其死亡重生后）

用户想法：*就算没有 LLM 驱动，也需要默认获得工具和装备以满足最低需求的动作；尤其是死亡后重生时，应该优先看箱子里有没有，然后就地做。*

设计草案（M2 再做，属"生存兜底"计划）：
- 默认目标（配方表 `bootstrap_kit`）：最低需求 = 武器（木/石剑或斧）+ 食物 + 镐（能挖石）。
- 优先级：**先搜箱子**（世界记忆/地点簿"家"附近的容器，`store_items` 的反向 `fetch`）→ 没有就**就地制作**（craft 配方链：木头→木板→木棍→木剑/木镐）→ 材料不够再出去采集。
- 触发时机：① 死亡复活后（`death` 事件 → 强制评估一次"我手上还有没有武器/食物"）② 空闲且缺最低装备超过 N 秒 ③ LLM 未驱动时作为自动兜底（受 11.1 冷却期约束）。
- 需要补的能力：`fetch_items`（从箱子取指定物品，`store_items` 的镜像）、配方链递归（craft 缺材料自动上游合成，M2 的"合成链"）、"我有武器吗"观测（已有 `weapon/weaponScore`，够用）。
