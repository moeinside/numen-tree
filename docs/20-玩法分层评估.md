# 20. 游戏内常用玩法分层评估：原子 / 战术 / 战略 / 本能

> 目的：在补战术库之前，先把"常用玩法"逐一判定层级，避免把**战略**当**战术**实现（例如 `craft_item`、`mine_nearby` 这类）。
> 判定依据：numen 全量 API（`docs/18`）+ 现有树技能/配方（`src/skills/*`、`src/recipes.mjs`）。

## 1. 判定规则（5 问）

按顺序问，命中即停：

1. **是不是一次 numen Lua 调用/一个物理动作？**（走一段、挖一格、放一格、挥一刀、吃一个、查一次）→ **原子**
2. **是不是 numen 内置反射负责？**（逃/防御/卡住/坠落/溺水）→ **本能**（树不实现）
3. **是否需要"先满足前置条件/依赖链"？**（要材料→材料要合成→要工具→要工作站）→ **战略**
4. **是否需要"在多个方案里选"？**（选配方/选材料/选路线/选目标/选工作站）→ **战略**
5. **能不能一句话定义成功、失败就重试或放弃，且只跨少数原子？** → **战术**
   否则 → **战略**

补充：
- **战术**允许小的 `if/循环`，但**不允许依赖规划**和**跨阶段目标切换**；
- **战略** = 目标 + 验收 + 依赖解析 + 战术编排 + 降级；战略只调用战术，不直接写原子；
- **本能** = mod 硬编码（`CoreReflexes`），树只让路+监听事件，不重复实现。

## 2. 分层定义

| 层 | 特征 | 例子 |
|---|---|---|
| 原子 | 单次 Lua 调用/单个动作，无规划 | 走 3 格、挖一格、放一格、`use.hit` 一次、`inv.eat` 一个 |
| 战术 | 有界单目标组合（≤十几秒），失败重试/放弃 | 找最近工作台、走到目标、打开工作台、合成一批、熔炼一批、指定目标攻击 |
| 战略 | 目标+验收+依赖树+跨战术编排+降级 | 做木镐、建安全屋、采集 N 木头、回家、找食物、守家 |
| 本能 | mod 反射链 | 逃、防御、脱困、MLG、溺水自救 |

## 9. 决策：numen 高层技能（含内部动作树）怎么用？

> 用户问题：numen MCP 技能本身可能包含战略级动作树（如 `inv.make`、`work.mine`、`move.to` 内部规划）。树工具应该**忽视它自己重建**，还是**直接用但留下打断**？哪个好？

### 9.1 结论（混合，不二选一）

**按"决策归谁"分三类：**

| 类别 | 判定 | 用法 |
|---|---|---|
| A. 决策归树，技能只执行 | 目标/配方/格子/数量/工作站已由树选定，技能内部只做执行（可能含路径规划这类**执行细节**） | ✅ **直接用**，包成原子/战术，加预算；跨 tick 的用长动作协议 |
| B. 执行很长，但决策已定 | 一个调用可能跑几秒~几分钟（`move.to` 长距离、`inv.smelt`、`fight.attack`） | ⚠️ **可以用，但必须分片或加"预算+急刹+settle+重观测"**；能用底层切片就切片 |
| C. 决策藏在技能内部，树本该自己做 | 技能自己选配方/选矿/选目标/选探索方向（`inv.make`、`work.mine`、`move.explore`、`fight.attack` 的目标选择） | ❌ **不用**（或只在"显式降级"时用并上报）；树用底层 API 自己编排 |

**一句话**：**执行可以借 numen，决策必须归树**；高层技能只有在"树已经把决策定死"时才值得直接用。

### 9.2 为什么不选纯"自己重建"

- numen 的路径规划/寻路、合成配方解析、掉落收集、容器 GUI 等是**mod 内部能力**，自己重建等于重写一套，成本高且不如它稳；
- 我们的 `move.to`/`work.dig`/`inv.craft` 等本来就是"numen MCP 技能"（用户原则：原子动作以 numen MCP 技能为基础单位）。

### 9.3 为什么不选纯"直接用 + 留打断"

- Lua 槽**不可优雅取消**：只能用补丁 `cutOff` 急刹，急刹后是 `detached`，必须 `settle` + 重新观测；
- 高层技能黑盒内部可能跑 17s~120s（实测 `fight.attack` >17s、`work.mine` 大簇 120s 超时），期间树**没有子步骤可见性、不能做每步预算、不能按原子边界抢占**；
- 会直接违反反混乱不变量（A1 三层预算、B1 一 tick 一个决策/一个原子、B3 防抖）；
- 黑盒还可能替树做错误决策（`inv.make` 不会换台、`work.mine` 选矿/路线不可控）。

### 9.4 具体 API 分类（按 2026-11-08 的 help 核对）

| numen API | 内部决策 | 建议 |
|---|---|---|
| `scan.*` / `status.*` / `inv.count/items/recipes/craftable` / `locate.*` | 无（只读） | ✅ 包成只读原子/战术 |
| `move.to(target,spec)` | 只规划**路线**，目标由树给 | ✅ 战术：短距离原子化；长距离由战略分片 |
| `route.plan` + `move.go` | 规划+整段走 | ⚠️ 可用 plan 做可见性；执行要分片 |
| `work.dig(cells)` | 格子由树给 | ✅ 原子/战术（有界格数） |
| `work.collect(radius)` | 范围由树给 | ✅ 战术（有界半径） |
| `build.place(design)` | 设计由树给 | ✅ 战术（有界格数） |
| `inv.craft(recipe,count)` | 配方由树给 | ✅ 战术（需已开格） |
| `inv.make(item,count)` | **自己选配方+台子+循环** | ❌ 战略级黑盒；树应 `recipes`+`craft` 自己编排（可作降级兜底并上报） |
| `work.mine(cluster)` | **自己选矿/找路/收集循环** | ⚠️ 仅当簇由树给出且数量有界时切片使用；否则不用 |
| `fight.attack(entity)` | 自己贴近/选武器/追击直到死亡/丢失/超距 | ⚠️ 长动作：目标已定 + 预算 + 超时急刹/settle；短兵相接优先 `use.hit` 循环 |
| `inv.smelt(furnace,item,count)` | 炉子/物品由树给，但**自己走过去+等** | ⚠️ 长战术：分片（放料/等待/取）或预算+急刹 |
| `move.flee(from,{distance})` | 距离由树给 | ⚠️ 本能已覆盖，仅显式命令时用 |
| `move.explore(dir,{until_})` | 自己找路/回调搜索 | ❌ 战略级；树自己用 `scan`+`move.to` 编排 |
| `move.follow(entity,{seconds})` | 目标/时长由树给 | ✅ 战术（有界时长）；持续跟随是战略行为 |
| `use.*` / `gui.*` / `gear.*` | 单步 | ✅ 原子/战术 |
| `task.stop` | 清理 | ✅ settle 原子 |

### 9.5 长动作协议（B 类必配）

对无法切片的高层调用（`fight.attack`、`inv.smelt`、长 `move.to`）：

1. 调用前：确认槽空闲、目标/参数已定、记预算（≤15s 原子或 ≤25s 战术）；
2. 超时/`detached`/`slot_blocked`：**先补丁急刹**（`cutOff`）→ `settle`（`task.stop`）→ 重新观测 → 由战略决定重试/降级/上报；
3. 同一长动作失败 3 次 → 熔断，不反复重派；
4. 绝不让一个黑盒调用无限占 tick。

### 9.6 对 Batch B/战略层的直接影响

- 制造：**不用 `inv.make`**；`craft_batch` 用 `inv.craft(recipe)`（配方由战略解析 `recipes`/`crafttree` 给出）；
- 熔炼：`smelt_batch` 用 `inv.smelt` 但分片+预算；
- 采集：`dig_cluster` 用 `work.dig(cells)`（格子由树给）；**不用 `work.mine` 自主选矿**；
- 战斗：自主交给本能；显式命令用 `attack_target`（`use.hit` 循环），不用 `fight.attack` 黑盒；
- 探索/回家：战略用 `scan`+`move.to` 分片编排，不用 `move.explore` 黑盒。

## 10. 环境分层执行策略（safe-batch / field-guarded）

> 用户提案：基地内安全环境 → 让 numen MCP 高层技能一口气跑完；野外遇险/被打断过一次 → 切换到树的"战略包模式"（细分、可中断）。
> 评估：**赞成**。这不是两套战略，而是同一套战略的**两种执行档位**，应做成独立的"执行策略层"。

### 10.1 分层位置

```
战略包（目标/验收/依赖/降级）
   └─ 执行策略层（本提案新增）：safe-batch 或 field-guarded
        └─ 战术/长动作（同一套战术库）
             └─ 原子 → numen Lua API
```

- **战略不变**：`make_item` 等战略在两种档位下是同一份代码；
- **执行档位只决定**：能不能用长黑盒技能、预算多大、抢占粒度多细、失败后怎么处理。

### 10.2 两个档位

| 维度 | `safe-batch`（安全） | `field-guarded`（风险） |
|---|---|---|
| 典型场景 | 合成/熔炼/建造/整理 | 出门采集/探索/战斗/长途 |
| 允许高层技能 | ✅ 可以用"决策已定"的长技能（`inv.craft`、`work.dig`、`inv.smelt`、`build.place`） | ❌ 只用战术/原子；长动作必须分片 |
| 单次预算 | 放宽（如 ≤60s，但必须有绝对上限+看门狗） | 收紧（原子 ≤15s，战术 ≤25s） |
| 抢占粒度 | 动作边界（粗） | 原子边界（细） |
| 失败处理 | 记录 + settle + 重试一次 | 立即 settle → 重新观测 → 降级/上报 |
| 中断风险 | 低 | 高（本能/敌人/地形） |

### 10.3 风险判定：只用行为证据，不用位置（用户修正）

> **不用"是否在基地"来判定安全**。基地被入侵时长任务照样会被打断；野外只要没有任何风险证据，也没必要强制细粒度。

**硬风险（立即降档；若长动作在飞→看门狗急刹+settle）**：

1. 收到 `reflex` 事件（本能出手 = 环境已不安全）；
2. 动作被抢占 / 超时 / `detached` / `slot_blocked`（"被打断过"本身就是危险证据）；
3. 受伤：`hp` 下降或 `hp% ≤ 50%`；
4. 敌对进入危险距离（`hostileCount > 0` 且 `hostileDistance ≤ 16`）；
5. 主人处于危险；
6. 危险方块贴近（岩浆/火/水，按 `scan.block` 可选）。

**软风险（降档，但不一定急刹）**：

- 饥饿 ≤ 6；
- 夜晚且无床/无光；
- 连续多次小失败（`no_path` 等）——可降档观察。

**位置不参与执行档位**：基地/锚点只影响**战略选择**（去哪干活、是否回家），不直接给"safe"资格。

**回到 safe-batch**：连续静默 N 秒（默认 30s）无硬风险事件 + HP/饥饿正常 + 附近无敌对。

### 10.4 切换规则（关键）

1. **默认乐观**：没有风险证据时允许 `safe-batch`（允许长技能一口气跑）；
2. **降档立即**：任一硬风险命中 → 立刻 `field-guarded`；
3. **长动作在飞时遇险**：例外允许**中途急刹**（补丁 `cutOff`）→ `settle` → 重新观测 → 转细粒度；不能等它自己跑完；
4. **升档滞后**：回到 `safe-batch` 需安静窗口（默认 30s，防抖）；
5. **打断后强制冷却**：任何一次 `preempted/timeout/detached` 后，强制 `field-guarded` 至少 60s，即使当下看起来安全；
6. **safe-batch 也必须有**：绝对时间上限、看门狗、`reflex` 事件监听、急刹+settle 能力。

### 10.5 与现有不变量兼容

- A1 三层预算：safe-batch 只是把"单动作上限"放宽到 `batchMaxSeconds`，仍然有上限；
- A2 硬抢占：safe-batch 下 P0/P1 仍可触发，但只能是"急刹+settle"（黑盒不可优雅取消）；
- B1 一 tick 一决策：safe-batch 的长调用占用 tick，但仍是"一个动作在飞"；
- B3 防抖：档位本身要防抖（降档立即、升档滞后）。

### 10.6 实现建议（后续）

1. 新增 `src/exec-policy.mjs`：`evaluateMode(state, cfg, now) → {mode, reason, until}` + 防抖/冷却；
2. lane 在**派发前**读档位：`safe-batch` 允许长技能/大预算；`field-guarded` 禁长黑盒、强制战术路径；
3. 长动作包装器：`runBatchAction(goal, {maxSeconds, watchdog, settle})`，急刹后必 settle+重观测；
4. 状态里暴露 `execMode/execReason/execSince` 给 `tree_status` 和 trace；
5. 测试：safe 批量完成、field 拒绝长技能、切换只在边界、打断后强制降档、防抖窗口。

### 10.8 长动作"三查"协议（用户补充：事前观测判安全）

**查一：事前观测（preflight，强制新鲜）**

- 长动作开始前，强制做一次**新鲜观测**（不接受缓存）：`hp/hunger/pos`、`hostileCount/hostileDistance`（半径放大到 24）、`ownerDanger`、最近风险事件；
- 判定阈值（建议默认）：
  - 无敌对在 **24 格**内；
  - `hp% ≥ 60` 且 `hunger ≥ 8`；
  - 最近 **30s** 内无 `reflex` / 抢占 / 超时 / `detached` / `slot_blocked`；
  - 主人不在危险状态；
  - 长动作**本身风险等级**允许（见下）。
- 任一不满足 → **不进入 safe-batch**，走 `field-guarded`（先处理风险/拆分动作）。

**动作风险等级（长动作分类）**：

| 等级 | 例子 | 允许 safe-batch |
|---|---|---|
| 低 | 基地内合成、熔炼、已知蓝图放置、整理 | ✅ 可 |
| 中 | 已知区域挖一小簇、短途移动 | ⚠️ 需 preflight 全过 |
| 高 | 挖矿下探、探索、跨地形长途、战斗 | ❌ 一律 field-guarded |

**查二：事中监控（长动作在飞时）**

- 事件循环持续监听 `reflex`、主人危险、任务结束；
- 看门狗：超过 `batchMaxSeconds`（默认 60s）→ 补丁急刹 + settle；
- 收到硬风险事件 → 立即急刹 + settle（不等跑完）；
- 承认盲区：长动作期间**观测不到周围**，只能靠事件/伤害/时长兜底。

**查三：事后观测（postflight，强制）**

- 长动作结束/被急刹后，**必须**重新观测一次；
- 用结果决定：成功继续 / 失败降级 / 上报；
- 若事后观测发现 HP 下降、附近敌对、位置异常 → 标记风险，强制 `field-guarded` 冷却。

**结论**：preflight 是必要条件，不是充分条件；三查缺一不可。

## 11. 扩展 mod 适配评估（武器 / 魔法 / 装置）

> 用户问题：如果玩家装了扩展功能模组（mod 武器、mod 魔法、mod 装置），当前"树工具 + numen MCP"能自主适配吗？

### 11.1 结论（分三层看）

| 层 | 对 mod 的适配 | 说明 |
|---|---|---|
| **numen 底层 API** | ✅ 相当通用 | 方块/物品/实体全用 id 字符串；`scan.*`、`move.*`、`use.*`、`gui.*`、`inv.*` 不限定原版；`fight.attack` 会**自己挑最强武器**（mod 武器可被识别）；`gear.hold/wear` 接受任意 id |
| **树的原子/战术** | ⚠️ 半通用 | 走 numen id 的动作能用 mod 物品（如 `gear.hold mod:sword`、`use.item`）；但**语义判定是白名单**：`eat_best` 只认固定食物表；`equip_best_weapon` 只匹配 `_sword/_axe`；工具检测按名字；工作站只找 `crafting_table/furnace` |
| **树的配方/战略** | ❌ 不自动适配 | `crafttree`/`recipes.mjs` 是**手写静态表**（原版向）；mod 物品没有配方链、没有战略目标；装置/魔法没有"能做什么"的语义 |

**一句话：底层"手"能碰 mod 东西，上层"知识"不认识 mod 东西。**

### 11.2 具体例子

| 场景 | 现在会怎样 |
|---|---|
| mod 剑 | ✅ 能用：`fight.attack` 自动选它；`gear.hold` 可拿；但"哪把最好"是 numen 内部判断，树不掌握 |
| mod 食物 | ❌ `eat_best` 白名单不认 → `no_food`；LLM 知道 id 可以用 `eat_one` 显式喂 |
| mod 工具（镐/斧） | ⚠️ `hasTool` 按原版 id 判断；`work.dig` 本身能挖、`scan.block` 有 `tool_right/digTime` 可辅助选工具 |
| mod 合成（工作台配方） | ⚠️ `inv.recipes/craftable/craft` 是通用的（mod 配方也能查/做）；但树的 `crafttree` 不生成这些目标 |
| mod 机器/装置 | ⚠️ `use.block` 能打开任意 GUI、`gui.*` 能点；但树没有"这台机器怎么用"的语义，也没有通用 GUI 战术 |
| mod 魔法/法术 | ❌ 大概率不行：numen 不暴露法力/法术注册表；只能靠 `use.item/use.block/gui.*` 手工交互，树不认识 |

### 11.3 怎么做到"尽量自主适配"（建议路线）

1. **数据化 profile（最划算）**
   - `data/roles.vanilla.json` + `data/roles.<modid>.json`：声明角色 → 物品/方块 id（武器、食物、工具、燃料、工作站、装置交互步骤）；
   - 按命名空间自动加载；未知命名空间走通用回退；
   - 把 `eat_best`/`equip_best_weapon`/`hasTool`/工作站查找改成读 profile，不再写死。
2. **通用回退（不依赖 profile 也能用一部分）**
   - 合成：`inv.recipes(item)` → `inv.craft(recipe)`（2×2/3×3）；mod 配方自动可用；
   - 工具：用 `scan.block().tool_right/digTime` 选工具，而不是名字猜；
   - 食物：先查 `inv.recipes`/标签；仍不行就上报让 LLM/主人指定；
   - 装置：新增只读 `inspect`（scan.container/gui.view）+ 通用"点一下 GUI"战术，由 LLM 决定点击顺序。
3. **LLM 作为"适配器"（探索模式）**
   - LLM 用 `tree_recipes` + 只读 inspect 看 mod 物品/机器；
   - 每次只做一个小实验（一个 `use.*`/`gui.move`），结果记进 memory；
   - 树提供 `tree_goal` 的通用交互战术，但**安全边界/预算**仍由树管。
4. **显式 adapter（魔法/复杂装置的现实解）**
   - 每个大 mod 写一个小 profile/脚本（交互序列），比"全自主推断"可靠得多。

### 11.4 不建议的做法

- ❌ 让树直接执行任意 Lua/任意 GUI 点击序列（安全和不可验证）；
- ❌ 试图从物品名猜所有语义（mod 命名千奇百怪）；
- ❌ 把 mod 物品硬编码进代码（每装一个 mod 就要改代码）。

### 11.5 对当前计划的插入点

- Batch B 的 `craft_batch` 已经走 `inv.craft(recipe)`（配方由 `inv.recipes` 给）→ **mod  crafting 配方天然兼容**；
- 下一步把 `eat_best`/`equip_best_weapon`/`hasTool` 从硬编码改成 **profile + 通用回退**；
- 装置/魔法等"语义型 mod"先不承诺自主，等 `inspect + 通用 GUI 战术` 再做。

## 12. 会话级知识表 / 临时图鉴（用户提案）

> 用户想法：有 mod 时树不认识它们；把 numen MCP 抓出来的 ID 留在树里当"知识"，比如临时表，游戏关了释放。

### 12.1 结论

**可行，而且应该这么做。** 这正是"让树自己长知识"的正确形态：不是静态 profile，而是**运行时观察 → 会话内记忆 → 用的时候可查**。

### 12.2 能自动学到什么（只读 API 就够）

| 知识 | 来源 | 说明 |
|---|---|---|
| 物品 id / 数量 | `inv.items()`（现有观测已含） | 每次观测顺手写入图鉴，零额外成本 |
| 物品**配方与依赖图** | `inv.recipes(id)` / `inv.craftable()` | JEI 式：id/station/makes/ingredients → mod 物品的合成链自动可学 |
| 方块 id / 硬度 / 适用工具 | `scan.block(cell)`（`BlockInfo.tool_right/digTime`） | 挖/看方块时顺手记录，可推断"这方块该用什么工具" |
| 实体 type/category/hp | `scan.entities()`（现有观测） | mod 生物也能记录类型/敌对分类 |
| 工作站与 GUI 布局 | `use.block` 返回的 Window / `gui.view` | 记录"这个方块是哪种 GUI、有哪些槽" |
| 掉落物/交易/容器内容 | `scan.container` / `scan.entities("item")` | 逐步补全 |

### 12.3 不能自动学到什么（要标注/实验/LLM）

- **语义角色**：`Stack` 只有 `item`+`count`，没有 tag/NBT/耐久/附魔 → 无法直接知道"这是食物/武器/燃料/魔法材料"；
- **效果**：`use.item` 会真的用掉，不能随便试（可做受限实验）；
- **法术/装置用法**：numen 不暴露 mod 的注册表/API，只能靠 GUI 观察 + LLM 经验。

所以：**ID/配方/方块属性可以自动学；角色语义需要"启发式 + LLM/主人标注 + 受限实验"。**

### 12.4 数据形态（会话内，不落盘）

```js
st.catalog = {
  sessionStartedAt, gameTime,
  items: { "mod:foo": { count, firstSeen, lastSeen, recipes: [...], roles: {...} } },
  blocks: { "mod:block": { hardness, toolRight, firstSeen } },
  entities: { "mod:mob": { category, hp } },
  stations: { "mod:table": { kind, guiSlots? } },
  labels: { "mod:foo": { food: true, weaponScore: 0.8, source: "llm"|"heuristic"|"experiment" } },
}
```

- **生命周期**：树进程内存；`numen.sessionGeneration` 变化（游戏重启/换档）→ 清空重建；树退出即释放（符合"游戏关了释放"）；
- 不写 world.json、不跨会话持久（避免把过期 mod 知识带进新档）。

### 12.5 树怎么用这张表

1. `eat_best`：先查 catalog.labels 食物，再查启发式（名字含 `_stew/_soup/_bread` 等），最后上报让 LLM/主人指定；
2. `equip_best_weapon`：catalog.labels 武器分数 → 否则启发式（`_sword/_axe/_bow/_staff`）→ 否则任意手持；
3. `hasTool`：用方块 `tool_right` 记录反推工具角色，而不是原版 id 白名单；
4. `query_recipes`/`craft_batch`：直接查 catalog 里缓存的配方（mod 合成链自动可用）；

### 12.7 上下文预算：图鉴不主动推（防上下文爆炸）

**原则：图鉴是树的内部记忆，不是给 LLM 的流水账。**

| 场景 | 给 LLM 什么 | 大小 |
|---|---|---|
| 平时 `tree_status` | **只给计数/增量**，如 `图鉴 42 物品 / 7 新配方`，不列 id | ≤ 30 字符 |
| 发现新物品/配方 | **不推送**，最多 trace；不进 tree_inbox | 0 |
| LLM 主动问 `tree_catalog` | 按过滤条件返回**小切片**：最多 10 条 / 每条约 100 字符 | ≤ 1KB |
| LLM 问某物品配方 | `tree_recipes(item)` 只返回该物品的配方（已实现） | ≤ 1KB |
| 策略需要时 | 树内部直接用，不经过 LLM | 0 |

**工具设计（建议）**：

```
tree_catalog(action: "summary" | "find" | "recipes" | "label", query?, item?, since_version?, limit?)
- summary：{version, items, blocks, entities, recipes, new_since_last}   // 极小
- find：query 匹配 id/前缀，最多 limit（默认 5，最大 10）→ [{id,count,roles?}]
- recipes：等价 tree_recipes(item)
- label：给 id 打会话内角色标签（LLM 可选写入，如 food/weapon/fuel）
```

**硬规则**：

1. 图鉴**永不**整表返回；`limit` 强制上限（默认 5，最大 10）；
2. 每条记录只给必要字段（id、count、roles），不给原始 JSON；
3. 新发现物品**只记 trace**，不主动进 inbox、不主动唤醒 LLM；
4. 只有"任务确实需要"时（LLM 问、战略要选材料）才查；
5. 惰性配方：只查当前关心的物品，不批量抓全库；
6. 定期压缩：图鉴只保留最近/相关的 N 条（如 200），旧记录摘要化。

**一句话**：图鉴越丰富，越要"按需切片"——丰富度留在树里，上下文里只出现当前决策需要的那几行。

## 13. 战略包的分层与优先级（用户提案）

> 用户直觉：单一功能性战略（造一个东西）是"低层级但高优先度"；造基地是"高层级但低优先度"。评估：方向正确，但**层级和优先级必须拆成两个独立轴**。

### 13.1 两个轴

| 轴 | 回答的问题 | 取值 |
|---|---|---|
| **层级 Level** | 这件事有多大/多复杂？（包含多少子目标） | L2 功能战略 / L3 工程战略 / L4 长期愿景（可选） |
| **优先级 Priority** | 现在有多急/多重要？做晚了会怎样？ | P0 救命 / P1 应急 / P2 主指令 / P3 当前目标 / P4 生产 / P5 维护 |

**不要用层级推优先级**：紧急避难所虽然"层级高"，但天黑前必须完成，优先级可以是 P1；而"整理仓库"层级低，却可以 P5。

### 13.2 层级定义

| 层级 | 名字 | 特征 | 例子 |
|---|---|---|---|
| **L2** | 功能战略 | **单一交付物 + 可数验收**，通常只调用战术包 | `make_item`（做 N 个某物）、`smelt_items`（熔炼 N 个）、`equip_best`（换最好的装备）、`store_items`（存一组）、`eat_until_full`（吃到饱） |
| **L3** | 工程战略 | **多交付物/多阶段**，调用多个 L2 或战术，有里程碑与验收 | `build_safe_house`、`build_farm`、`bootstrap_kit`（工具+武器+工作台）、`prepare_for_night`（床/火把/食物/围墙）、`establish_base`（选址+清理+建造+储物）、`explore_find`（探索找资源/群系） |
| **L4** | 长期愿景（可选） | 跨天/跨工程，持续目标 | "活得好"（食物储备+安全屋+装备升级）、"探索世界"——建议只由 LLM 给方向，树拆成 L3 |

### 13.3 优先级判定规则

按"如果不做，多久会出问题 / 是否错过窗口"：

| 优先级 | 判定 | 例子 |
|---|---|---|
| P0 | 立即致命，但通常归**本能反射** | 逃跑/防御/溺水 |
| P1 | 短窗口、不做马上疼 | 天黑前没床、被怪围、饥饿到临界 |
| P2 | 主人/LLM 明确指令 | "给我做把剑" |
| P3 | 当前目标链上的必要步骤 | 做木镐前先做工作台 |
| P4 | 生产/改善，可延后 | 批量熔炼、整理仓库 |
| P5 | 维护/美化，空闲才做 | 铺路、装饰、分类箱子 |

**动态修正**：`prepare_for_night` 白天 P4、太阳快落 P1；`eat` 饥饿>10 P4、≤6 P1。

### 13.4 战略包注册表字段（实现约定）

```js
{
  id: 'strategy.make_item',
  level: 2,                    // 2=功能战略, 3=工程战略
  defaultPriority: 40,         // P3 左右；调用方/LLM 可覆盖
  priorityHints: { night: 60, ... }, // 可选动态修正
  preemptible: true,           // 能否被更高优先级在战术边界抢占
  budget: { maxSeconds, maxTactics, maxSubStrategies },
  acceptance: (state, ctx) => boolean,   // 可数验收
  decompose?: (state, ctx) => Goal[],    // L3：拆成子目标（L2/战术）
  run: async (ctx, params) => Result     // L2：直接编排战术
}
```

### 13.5 调度规则（关键）

1. **优先级决定"什么时候跑"**：取最高优先级的 ready 目标；同级时**短任务优先**（响应性）；
2. **层级决定"怎么展开"**：L3 不一口气跑完，先 `decompose` 成子目标，逐个执行、检查里程碑；**每完成一个子目标回到调度器重新判优先级**（可被更急的事打断）；
3. **高优先级可抢占低优先级**：在**战术边界**抢占；L3 被抢占时保存进度（project state），恢复时从下一个未完成子目标继续；
4. **防饿死**：低优先级 L3 长期排不上队时，定期上报一次（`project_starved`），让 LLM/主人决定是否提权；
5. **不跨层直接跳**：L2 不直接写原子；L3 不直接写原子，也不绕过 L2/战术；
6. **LLM 显式指令可以提权**，但不能把 L3 当 L2 一步跑完。

### 13.6 例子

| 场景 | 层级 | 优先级 |
|---|---|---|
| 主人说"给我做把木剑" | L2 `make_item` | P2 |
| 天快黑了，先做床/火把 | L3 `prepare_for_night`（拆：`make_item`床→放床） | 动态 P1 |
| 建安全屋 | L3 `build_safe_house` | P4（被 P1/P2 抢占） |
| 批量熔炼 32 铁 | L2 `smelt_items` | P4 |
| 整理仓库 | L3 `organize_storage` | P5 |
| 探索找新基地 | L3 `explore_find` | P4（但路上遇险立刻被本能/中断压过） |
