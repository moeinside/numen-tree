# 99. 评审分工（纠偏）

> 2026-11-10。Lead 之前把架构细节交给 PM 审，越权；现固定如下。

## 角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| `idea-king`（架构红队） | 架构方案、边界、失败模式、是否过拟合 | 阶段验收签字 |
| `project-steward`（总控） | 方向、优先级、非目标、全局风险 | 具体实现方案 |
| `product-architect`（PM） | **阶段验收**：范围、验收条件、assisted/Track A 口径、是否进入下一阶段 | 架构方案细节 |
| `mc-expert` | 游戏机制、能力/带宽、Day1 可观测性 | 验收签字 |
| `behaviorist` | 行为/自主性/抢占语义 | 架构实现 |
| `player-rep` | 玩家期望、外援/死亡有界 | 技术方案 |
| `hr-advisor` | 顾问团完整性 | 技术/验收 |

## 流程

```text
设计草案
→ 架构师（idea-king）审架构
→ 总控（project-steward）确认方向/非目标
→ 实现
→ PM（product-architect）只审阶段验收
```

## 评审频率（纠偏）

不过度审：

- **每个里程碑**交架构师一次（不是每轮/每个小修都交）；
- **一个大阶段**完成才交 PM 验收（Phase A / Phase B / Phase C）；
- 中间小修、测试、字段调整由 Lead 自检，不拉人；
- 只有架构红线/口径变化才提前升级。

## P0-0b 里程碑

| 里程碑 | 架构评审 | PM |
|---|---|---|
| M1 优先度契约 + 显式 consequence | 一次 | — |
| M2 action-tx/current 生命周期 | 一次 | — |
| M3 真实 lane 三场景 + 中间件收口 | 一次 | — |
| M4 Phase B 完成 | 汇总 | Phase B 验收 |
| M5 Phase C 持久化/真实 trace | 一次 | Phase C 验收 |

## 当前 P0-0b 对应

- 架构：priority 分层、atom 边界、action-tx 中断记账、current 生命周期 → `idea-king`
- 方向/非目标：不照抄测试员、不 LLM 仲裁、不改 Day1 口径 → `project-steward`
- 阶段验收：Phase A/B 是否通过、是否进入下一阶段 → `product-architect`
