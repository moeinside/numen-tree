# 战术包第一批（数据表 v0，待审）

> 目的：把"原子动作 → 战术包"这一层先定成**数据**，供调度器消费。本文只是设计稿，**未写代码**。
> 依据：`docs/17`（底层审计/实验）、`docs/18`（能力全表/实测判定）。
> 三条硬约束（来自实验）：
> 1. 每同伴只有**一个 Lua 槽**；原子=一次 Lua，目标 3~10 秒返回；
> 2. 长动作（`move.go` detach、大簇 `work.mine`）不可控 → 要么拆，要么"急刹 + settle"；
> 3. 急刹（cutOff）能抢回槽，但**残留 detach 任务可能继续推身体** → 急刹后必须先 settle。

---

## 0. 约定

| 概念 | 约定 |
|---|---|
| **原子** | `atom.<id>`：一次 Lua 程序，参数校验、超时预算、返回结构化结果 |
| **战术包** | `tactic.<id>`：数据表（原子序列 + 循环 + 成功条件 + 重试/降级），运行时是状态机 |
| **优先级** | P0 救命 → P5 待命（调度器按此抢占） |
| **抢占** | `soft`=原子边界换；`hard`=允许急刹（配 settle） |
| **schema** | `schemaVersion:1`；`steps[].op` 走注册表；未知 op/字段→警告/拒绝，不崩溃；`ext` 自由扩展 |

## 1. 原子注册表 v0

每个原子 = 一个 Lua 程序模板（参数注入），必须在预算内返回紧凑 JSON。

| 原子 | 对应 numen API | 参数 | 预算 | 可硬刹 | 返回 | 备注（实测） |
|---|---|---|---|---|---|---|
| `atom.observe_fast` | `status.self/world/owner` + `scan.entities(hostile,16)` | — | 1s | 是 | `{hp,hunger,pos,ownerDist,hostileN,hostileD,dark}` | 树现有快观测；合并一次 Lua 省槽 |
| `atom.observe_full` | 上面 + `inv.items` + `scan.entities(item/passive)` | `radius` | 2s | 是 | 扩展版 | 慢观测 |
| `atom.scan_block` | `scan.block(cell)` | `cell` | 1s | 是 | `{name,is_air,in_reach,hardness,...}` | BlockInfo 用 `.name` |
| `atom.scan_blocks` | `scan.blocks(ids,{radius})` | `ids,radius` | 2s | 是 | `{count, clusters:[{nearest:{pos}}]}` | 大簇可上千块，勿直传 mine |
| `atom.scan_entities` | `scan.entities(type,{radius})` | `type,radius` | 2s | 是 | `[{id,name,distance,pos}]` | 观察/找猎物 |
| `atom.inv_count` | `inv.count(item)` | `item` | 1s | 是 | `n` | — |
| `atom.inv_items` | `inv.items()` | — | 1s | 是 | `[{item,count}]` | — |
| `atom.move_segment` | `move.to(target,{arrive})` | `target,arrive,maxBlocks` | 6s | 是 | `{ok,pos,distance_left}` | 限距/限时；`arrive=near` 停 ~3 格 |
| `atom.route_plan` | `route.plan({to,arrive})` | `to,arrive` | 2s | 是 | `{ok,plan?}` | 只规划不移动，便宜 |
| `atom.dig_one` | `work.dig(cell,{count:1})` | `cell` | 6s | 是 | `{ok,block,air}` | 单格 ~1.7s；掉落常自动拾取 |
| `atom.collect_near` | `work.collect({radius})` | `radius` (≤8) | 8s | 是 | `n`（捡到数） | r4≈1s / r8≈2.4s |
| `atom.attack_one` | `fight.attack(entity)` | `entityId` | 8s | 是 | `{ok,fought}` | **只打可达目标、不走路** |
| `atom.eat_one` | `inv.eat(item)` | `item` | 3s | 是 | `{ok,ate}` | 需背包有食物 |
| `atom.hold_item` | `gear.hold(item,{hand})` | `item,hand` | 1s | 是 | `{ok}` | 换手/战斗前 |
| `atom.place_one` | `build.place({cells})` | `cell,item?` | 3s | 是 | `{ok,placed}` | 需支撑/材料 |
| `atom.task_stop` | `task.stop({task_id?})` | `taskId?` | 1s | 是 | `{ok}` | 急刹/清理残留 |
| `atom.settle` | `task.stop()` + `status.self` + `scan.entities(item,4)` | — | 3s | 是 | `{task:nil,pos,items}` | **急刹后必跑**：顶掉残留 detach 任务、确认位置 |

**原子纪律**：禁止出现超过 15s 的原子；超过的一律拆成战术包（大簇 mine、smelt 等待、move.go 整段）。

## 2. 第一批战术包（8 个）

优先级：P0 救命 / P1 应急 / P2 LLM 覆盖 / P3 目标 / P4 生产 / P5 待命。

### 2.1 `tactic.move_segment`（移动一段）

| 项 | 内容 |
|---|---|
| 用途 | 朝目标走一小段；所有移动类战术的基元 |
| 优先级 | P3（被 P0/P1 战术调用时可提权） |
| 抢占 | soft |
| 预算 | maxSeconds 8 / maxTries 2 |
| 序列 | `observe_fast` → `move_segment{target,arrive}` → 成功判定 |
| 循环 | 重复直到 `distance_left ≤ arriveRange` 或 tries 用尽 |
| 成功 | 距目标 ≤ arriveRange |
| onFail | `no_path`→重试1次→仍失败 `abort`；`out_of_reach`→abort |
| 备注 | 大目标要拆成多个 waypoint；每次 ≤10 格 |

### 2.2 `tactic.dig_one`（挖一格并拾取）

| 项 | 内容 |
|---|---|
| 用途 | 把一个指定格子挖掉，掉落尽量捡起 |
| 优先级 | P4（P0 脱困挖墙时可提权） |
| 抢占 | soft |
| 预算 | maxSeconds 10 / maxTries 1 |
| 序列 | `scan_block{cell}` → 若 `!in_reach` 则 `move_segment{cell, arrive=3}` → `dig_one{cell}` → `collect_near{radius=4}` |
| 成功 | 复扫 `is_air=true`；若期望掉落则 `inv_count` 增加 |
| onFail | `out_of_reach`→再 move 后重试1次；`no_path`→abort；`unbreakable/needs_tool`→abort 并上报 |
| 备注 | 挖前先 `hold_item` 正确工具（战术外由调度器插入） |

### 2.3 `tactic.eat_one`（吃一口）

| 项 | 内容 |
|---|---|
| 用途 | 饥饿时吃东西 |
| 优先级 | **P0** |
| 抢占 | hard |
| 预算 | maxSeconds 4 / maxTries 1 |
| 序列 | `inv_items` → 选一种食物 → `eat_one{item}` → `observe_fast` |
| 成功 | hunger 上升 或 食物数量减少 |
| onFail | 无食物→`abort` 并上报 ★ |
| 备注 | 食物清单白名单（bread/apple/carrot/potato/…）；P0 允许打断任何软动作 |

### 2.4 `tactic.flee`（逃）

| 项 | 内容 |
|---|---|
| 用途 | 从威胁撤到安全距离 |
| 优先级 | **P0** |
| 抢占 | hard |
| 预算 | maxSeconds 12 / maxTries 3 |
| 序列 | `observe_fast` → 计算远离方向 → `move_segment{方向点}`；循环直到 `hostileD ≥ safeDist` 或无敌人 |
| 成功 | 最近敌对 ≥ safeDist（默认 12）或无敌对 |
| onFail | `no_path`→换一个方向（最多2次）→仍失败 `abort`（原地防御/上报） |
| 备注 | 逃跑方向先 `scan_block`/`scan.map` 粗检，避免退进岩浆/水 |

### 2.5 `tactic.attack_one`（打一次/打一个）

| 项 | 内容 |
|---|---|
| 用途 | 攻击一个目标直到死亡/丢失 |
| 优先级 | P1 |
| 抢占 | soft（紧急可 hard） |
| 预算 | maxSeconds 15 / maxTries 3 |
| 序列 | `scan_entities{hostile/passive}` → 若目标不在可达距离 `move_segment{target,arrive=2}` → `hold_item{武器}` → `attack_one{entityId}` → 复查 `scan_entities` |
| 成功 | 目标从扫描中消失（死亡/逃跑） |
| onFail | `not_found`（不可达）→重试移动1次→abort；`out_of_reach`→同左 |
| 备注 | 实测 `fight.attack` 不走路；必须自己先 move |

### 2.6 `tactic.collect_near`（捡附近掉落）

| 项 | 内容 |
|---|---|
| 用途 | 捡半径内掉落物 |
| 优先级 | P2（战斗/食物后） / P4 |
| 抢占 | soft |
| 预算 | maxSeconds 8 / maxTries 2 |
| 序列 | `collect_near{radius=4}` → 若返回 0 → `scan_entities{item,radius=8}` → 最近一个 `move_segment` → 再 `collect_near{4}` |
| 成功 | 捡到 ≥1 或原来就没有掉落物 |
| onFail | 0 且无掉落→`done(empty)`；`no_path`→abort |
| 备注 | 实测 r4≈1s / r8≈2.4s；返回数量 |

### 2.7 `tactic.come_home`（回家/回主人附近）

| 项 | 内容 |
|---|---|
| 用途 | 自主模式回锚点（家/主人附近） |
| 优先级 | P3（牵引绳/待命） |
| 抢占 | soft（move.go 段可 hard + settle） |
| 预算 | maxSeconds 30 / maxTries 2 |
| 序列（安全版） | `route_plan{to: 锚点}` → 若 `plan.ok` 则按 10 格拆 waypoint，循环 `move_segment`；失败则 `backoff` 2 格重试 |
| 成功 | 距锚点 ≤ range（默认 4） |
| onFail | `no_path`→backoff+放宽 range（6/8）→仍失败 `abort` 并上报（下一阶段接"区域目标"） |
| 备注 | **默认不用 move.go**（detach 残留难处理）；仅当 waypoint 循环太慢时启用 move.go + 急刹 + `atom.settle` |

### 2.8 `tactic.find_food`（找吃的）

| 项 | 内容 |
|---|---|
| 用途 | 自主模式找食物 |
| 优先级 | P4（饥饿 P0 时由 eat 先处理库存；无库存才升级） |
| 抢占 | soft |
| 预算 | maxSeconds 60 / maxTries 1 |
| 序列 | `scan_entities{passive,32}` → 有猎物：`attack_one`→`collect_near`→`eat_one`；无猎物：`scan_entities{item,16}`→捡起可食物→试吃；仍无→`abort` 上报 ★ |
| 成功 | 饥饿回升 或 背包食物数 >0 |
| onFail | 无猎物/无食物→abort 上报（不要无限逛） |
| 备注 | 只做"最近邻"猎物，不追远；找吃的属于长任务，实际由**战略包**编排，本战术只是其中一段 |

## 3. 数据格式（示例，schemaVersion 1）

```jsonc
{
  "schemaVersion": 1,
  "kind": "tactic",
  "id": "tactic.dig_one",
  "title": "挖一格并拾取",
  "priorityClass": "P4",
  "owner": "tree",
  "preempt": "soft",
  "budget": { "maxSeconds": 10, "maxTries": 1, "maxAtoms": 6 },
  "steps": [
    { "op": "atom.scan_block", "as": "b", "cell": "$target" },
    { "op": "if", "when": { "op": "not", "of": { "op": "field", "of": "$b", "field": "in_reach" } },
      "then": [{ "op": "atom.move_segment", "target": "$target", "arrive": 3 }] },
    { "op": "atom.dig_one", "cell": "$target" },
    { "op": "atom.collect_near", "radius": 4 }
  ],
  "success": { "op": "scan_block_is_air", "cell": "$target" },
  "onFail": { "no_path": "abort", "out_of_reach": "retry:1", "unbreakable": "abort" },
  "ext": {}
}
```

**扩展性保证**：`schemaVersion` 递增；`steps[].op` 注册表；未知 op→加载警告并拒绝该包；未知字段忽略；条件也用 op 表示；`ext` 自由区；`capabilities` 声明所需能力（换游戏时校验）。

## 4. 调度器接口（战术包 ↔ 原子）

```
调度器每拍：
  1) 选最高优先级可运行战术包（P0/P1 可抢占）
  2) 取出该战术包的"下一个原子"（状态机 cursor）
  3) 若上一个原子被 hard 打断 → 先跑 atom.settle
  4) 执行原子（一次 Lua）→ 结果写回战术包状态机
  5) 成功/失败/重试/降级 → 更新包状态；结束则回到第 1 步
```

- 战术包状态：`{cursor, tries, vars, startedAt, atomsRun}`；
- 原子执行结果统一结构：`{ok, kind, data}`；
- **settle 协议**（急刹后）：`atom.settle` → 采样两次位置确认稳定 → 才允许派下一个原子。

## 6. 自查结论（2026-11-08，推荐方案，待你点头）

> 你说"无法估价"是正常的——这些不是喜好题，是**代价题**。每个选择下面都写清"为什么、放弃了什么"。

### Q1 原子实现方式：推荐「共享执行壳 + 原子注册表 + JS 参数校验」

```
atom 定义（JS 对象/函数）:
  { id, params: {schema}, build(params) -> { luaBody, timeoutMs, settle? }, parse(result) }
共享执行壳（一个）:
  LUA_PRELUDE + 参数安全注入(luaLiteral) + 统一回执 JSON + 超时 + 错误包装
```

- 不用「每个原子手写完整 Lua 字符串」：25+ 个原子会重复 prelude/回执格式，改一处要改 25 处，参数注入也容易出坏代码；
- 不用「JS 编译任意 Lua」：黑盒、难审、也破坏了"一次 Lua 只做一个动作"的纪律；
- 代价：写新原子比贴字符串略慢——换来统一校验/回执/测试。

### Q2 战术包控制 op：最小集 **atom / call / if / retry / until**（+ 隐式 `as`/`set`）

| op | 用途 | 限制 |
|---|---|---|
| `atom` | 调一个原子 | 必须注册；一次一个 Lua |
| `call` | 调另一个战术包 | 只允许声明过的包；嵌套 ≤2，禁递归 |
| `if` | 条件分支 | 条件也是 op 树（field/eq/lt/gt/and/or/not/exists），**不写 JS 表达式** |
| `retry` | 包裹子序列 | `maxTries` 必填；按失败类型映射 |
| `until` | 循环直到条件 | `maxRounds` 必填；超时由调度器兜底 |

- 不做：`while`（until 覆盖）、`parallel`（单槽无并行意义）、任意表达式/脚本；
- 三层兜底防失控：`maxRounds`（包内）+ `maxAtoms`（调度器）+ `maxSeconds`（墙钟）；
- 放弃表达力，换"数据可读、可离线测、不会失控"；真需要更强时优先"拆更多战术包 + call"，而不是加语言特性。

### Q3 第一批样板：**move_segment / dig_one / eat_one / settle**（4 个）

正好覆盖四个基础风险：
1. `move_segment`：移动原子 + until 循环 + 距离成功判定；
2. `dig_one`：多原子序列 + reach 回退 + collect；
3. `eat_one`：P0 硬优先级 + 背包读取；
4. `settle`：急刹后清理 detach 残留（实验发现的唯一硬坑）。

`flee/attack_one` 要有真实敌对场景，`find_food/come_home` 依赖战略层 → 都放第二批。

### Q4 find_food / come_home：做成「组合片段（call 其它战术包）」，不独立造 Lua

- `find_food` = `scan/attack/collect/eat` 的组合；`come_home` = `route_plan + move_segment` 组合；
- 它们**由战略包调用**（自主模式），本身不发明目标；
- 第二批实现，先用回放里的"假战略包"驱动测试。

## 8. 抗打断 / 防混乱：硬不变量（用户期望的两条保证）

> 用户要求：① 不会因为一个长动作被打断而陷入混乱和大量死循环；② 不会因为打断而陷入决策混乱。
> 结论：**能满足，但必须靠下面 6 条硬规则 + 回放验收**；不是"设计得好自然就不会"。

### A. 防"打断后混乱 / 死循环"（3 条）

| # | 硬规则 | 强制点 |
|---|---|---|
| A1 | **三层预算，任何循环都有上限**：原子 ≤15s；战术包 `maxAtoms`（如 30）+ `maxSeconds`（如 60）；全局每目标 `maxGoals` | 调度器在**派原子之前**计数，超了直接 abort + 上报，绝不进入下一轮 |
| A2 | **急刹是"受控停车"，不是"半路放弃"**：只有 P0/P1 或 `preempt:hard` 可急刹；急刹后**强制 settle**（task_stop + observe + 位置采样两次）再派下一个原子 | `tactic-runner` 状态机：`active → preempted → settling → resumed/aborted`，少一步都拒绝 |
| A3 | **不重试同一失败**：同一战术包同一 `failKind` 连续 3 次 → 熔断（abort + 上报 + 冷却），禁止自动无限重试 | 战术包内 `retry` 的 maxTries + 调度器级"同错熔断"双层 |

**针对 `move.go` 的特殊处理**：它是 detached（实验证明急刹后身体可能继续动），所以：
- 默认**不放进常规战术**；仅作"走不动时的兜底"；
- 一旦启用，**必须**配 settle；settle 后位置若仍在变 → 再 settle 一次，仍变 → abort + 上报（不硬等、不循环）。

### B. 防"打断后决策混乱"（3 条）

| # | 硬规则 | 强制点 |
|---|---|---|
| B1 | **每拍只有一个决策者、一个动作**：安全(P0/P1) > LLM 覆盖(P2) > 目标(P3) > 生产(P4) > 待命(P5)；同级先进先出 + 防饿死提权 | 调度器单入口；任何层都不能绕过它直接发 Lua |
| B2 | **一切以现场观测为准**：战术包被挂起/恢复时，不假设世界没变（目标可能死了/方块没了/位置变了）；恢复第一个动作必须是 `observe_*` 重新校验，不满足就 abort 换备选 | `tactic-runner.resume()` 强制先 observe；状态机状态不跨"事实失效" |
| B3 | **不抖动**：同一战术包在 30s 内被打断 ≥3 次 → 判定"环境不允许它做"，挂起并上报 ★；危险解除需要满足持续条件才恢复（不是一有风吹草动就切） | 调度器的抢占计数 + 肾上腺素模式的进入/退出迟滞 |

### C. 回放验收（这两条保证必须能测出来）

| fixture | 断言 |
|---|---|
| `preempt_settle` | P4 战术执行中插入 P0 → 只允许一个"在途原子"；急刹后 `settle` 被调用；之后要么恢复原战术（重新 observe），要么干净 abort；**无重复副作用** |
| `no_infinite_loop` | 故意构造"永远不满足 until 条件"的战术 → 在 `maxAtoms` 处停止并上报；回放 tick 数有上限 |
| `same_fail_breaker` | 同一 failKind 连续 3 次 → 熔断，不再重试；只上报一次 |
| `thrash_guard` | 30s 内被打断 3 次 → 挂起 + ★ 上报，不再被同一环境反复拉起 |
| `orphan_resume` | 被打断后目标已消失 → 恢复时 observe 发现，干净 abort（不是继续对着空气做事） |
| `slot_hang` | 模拟 Lua 卡死 → 只调用一次 unlock → settle → 若仍不可用则 abort + ★，**不重试风暴** |
| `budget_caps` | 战术包 maxSeconds/maxAtoms 到顶 → 停止，状态机进入 failed/reported，不是 blocked |

### D. 诚实的边界（这两条保证的代价）

1. **不保证"瞬间停住"**：游戏侧 detach 任务有残留，急刹 + settle 后可能还有 1~3 秒身体惯性；保证的是"**有界**（几秒内停/被替换）+ **可观察**（状态上报）+ **可继续**（恢复前重新观测）"。
2. **不保证"所有目标都完成"**：预算/熔断会主动放弃并上报——这是防混乱的代价。
3. **依赖 lockfix 补丁**：急刹/清残留靠 8768 补丁；补丁不在时降级为"等超时 + 直接 abort 上报"，不会死循环。

## 15. 本能 vs 树：边界重划（2026-11-08 17:1x，用户观察确认）

> 用户观察：内置脑本来就有多种反射；**给了一把剑后，内置脑直接开打，而不是逃跑**。结论：本能负责生存反射，树不要重复。

### 15.1 已确认的内置反射（来自 numen jar `CoreReflexes`）

| 反射链 | 负责 | 是否可配置 |
|---|---|---|
| `FleeChain` | 打不过就跑/被围脱离 | ❌ 硬编码 |
| `MobDefenseChain` | 身边有威胁 → 防御/开打 | ❌ 硬编码 |
| `UnstuckChain` | 卡住 → 自行脱困（漫游/转向） | ❌ 硬编码 |
| `MLGChain` | 高处坠落 → 尝试水桶落地 | ❌ 硬编码 |
| `BreathChain` | 水下窒息 → 上浮/找空气 | ❌ 硬编码 |

- 配置目录只有 **LLM 内置脑**的 provider/binding（当前同伴没绑），**没有反射开关**；
- Lua API / MCP 工具也没有"暂停反射"的接口；
- 反射选择受**装备**影响：有武器时倾向 MobDefense，没武器倾向 Flee（用户实测）。

### 15.2 边界（新）

| 能力 | 归属 | 说明 |
|---|---|---|
| 逃跑 / 防御 / 打身边威胁 | **numen 本能** | 树不抢、不重复；只监听 `reflex` 事件 |
| 卡住脱困 / 坠落 / 溺水 | **numen 本能** | 树不重复 `survive_unstick`/`survive_hazard` |
| 吃（饥饿） | **树** | 反射链列表里没有"吃"；树保留 `survive_eat` |
| 找食物 / 生产 / 建造 / 存物 | **树** | 需要规划，本能不做 |
| 指定目标攻击（主人说"打那只"） | **树（战术命令）** | `attack_target` 保留，但作为 P2 显式命令，不是自主 P0 |
| 上报/调度 | **树** | 本能不会上报 |

### 15.3 协调规则（替代"抢槽"）

1. 树监听 `get_events` 的 `reflex` 事件：收到后进入 `instinctBusy`，**暂停派新动作、等待槽空**；事件结束（槽空闲/无新 reflex）后重观测恢复；
2. `a program is already running ... built-in brain is acting` 时：
   - 查补丁 `/status`：`count>0` → 程序遗留（僵尸锁），才 `unlock`；
   - `count==0` → **本能占用，等待**，不硬刹、不抢槽；
3. 树自有生存战术缩减：
   - **保留** `survive_eat`（饥饿）；
   - `survive_flee` / `survive_fight` / `survive_unstick` / `survive_hazard` 降级为"本能不在时（未来若能临时关闭）或 LLM 显式请求"才用，**不再作为自主 P0**；
   - `attack_target` 保留为 **P2 战术命令**（如主人点名目标），使用前先确认槽空闲/无近期 reflex。

### 15.4 原子动作基线（继续遵守）

- 原子动作只基于 **numen MCP/Lua 已有动作**（`docs/19 §14` 对照表）；
- 不新增"自己发明"的动作；`swing_once` = `numen.use.hit`、`move_flee` = `numen.move.flee` 等；
- 反射由 mod 实现，树不复制。

### 15.5 对现有战术包的影响

| 战术包 | 调整 |
|---|---|
| `survive_eat` | 保留（树自主 P0） |
| `survive_flee` / `survive_fight` / `survive_unstick` | 标记 `deprecated`（或仅在显式模式下启用）；不参与自主调度 |
| `attack_target` | 保留为 P2 显式战术命令 |
| 其他生产类 | 不变 |

### 15.6 下一步

1. 实现 `instinctBusy`（事件监听 + 槽占用判定 + 自动恢复）；

## 16. 制造与配方查询（LLM 介入不改变战术/战略设计）

### 16.1 numen 侧的配方能力（实测/文档确认）

| API | 能力 | 备注 |
|---|---|---|
| `numen.inv.recipes(item)` | JEI 式：该物品的**所有**配方（id/station/item/makes/ingredients），只读、瞬时 | 找不到 = 只能挖/交易 |
| `numen.inv.craftable()` | 当前背包材料**立刻能做**的配方 | 只读、瞬时 |
| `numen.inv.craft(recipe,{count})` | 在**已打开**的合成格里做一次（支持 count） | **不走路、不开台子**；3×3 需先 `use.block` 开工作台 |
| `numen.inv.make(item,count)` | 自动选配方+台子，做到够数 | 已知坑：不会换台/坏台会失败 |
| `numen.inv.smelt(furnace,item,count,{fuel})` | 走到熔炉、放料、等、取 | 长动作（要分片） |

### 16.2 现在"树工具"能不能查配方？

- **能拿到数据，但没有接口暴露**：树进程内部可以执行这些 Lua API；但当前树 MCP **没有**"查配方"工具，且现有 `craft` 技能用的是**树自己的静态 `crafttree`**，不读 numen 动态配方。
- 结论：
  1. 树内部：新增**只读原子** `recipe_query` / `craftable`，供 `craft_item` 战术使用；
  2. 给 LLM：建议新增只读 MCP 工具 **`tree_recipes`**（参数 item 或空=craftable），返回精简配方列表；否则 LLM 只能通过战术间接问。

### 16.3 LLM 介入时，制造战术/战略要不要单独设计？

**不需要两套实现，只需要"同一套数据 + 不同权限/参数来源"**：

| 层 | 自主（无 LLM） | LLM 介入 |
|---|---|---|
| 战术包 | `craft_item(item,count)` 等**同一套** | 同一套（LLM 只传 item/count） |
| 战略包 | 树自主选目标（做工具/建屋） | LLM 给意图/验收；战术不变 |
| 优先级/权限 | P4 生产 | P2/P3（按 LLM 指令提权） |
| 配方来源 | 优先静态 `crafttree`（快、可控） | 静态没有时用动态 `inv.recipes` 兜底 |

**唯一需要为 LLM 单独做的**：一个"查配方"只读工具（`tree_recipes`），让 LLM 能问"这东西怎么做/现在能做什么"，而不是让 LLM 直接写 Lua。

### 16.4 `craft_item` 战术的设计要点（Batch B 用）

1. **配方选择**：`crafttree` 有 → 走链（树已知安全）；没有 → `recipe_query(item)`；
2. **材料检查**：`inv.craftable()` 或对照 ingredients；缺料 → 结束并上报（不硬做）；
3. **工作站**：
   - 2×2（玩家格子）：直接 `craft_one`；
   - 3×3：`find_block("crafting_table")` → 没有则 `place_one`（做台子）→ `use_block` 开台 → `craft_one`；
   - 熔炼：`smelt_batch`（长动作，原子分片：放料/等/取）；
4. **验证**：`inv.count(item)` 前后差 ≥ 期望；
5. **不依赖** `inv.make`（换台/坏台不可靠），必要时才降级使用并上报。

### 16.5 建议下一步

1. 新增原子：`recipe_query`、`craftable`、`craft_one`、`open_table`（use.block+确认 Window）、`smelt_batch`（分片）；
2. 新增战术：`craft_item`、`smelt_item`、`gather_block`（Batch B 其余）；
3. 新增只读 MCP 工具 `tree_recipes`（给 LLM 问配方用）；
4. 回放测试：有料/缺料/需要 3×3 台子/坏台/无配方五种分支。

## 17. 制造的分层修正：制造是战略包，战术只做"单步能力"（2026-11-08 17:3x，用户洞察）

> 用户判断：造东西整体应该是**战略包**；战术层只有"找工作台 / 移动到工作台 / 检索材料"这类单步动作。评估：**正确**，之前把 `craft_item` 当战术包是高估了战术层。

### 17.1 判定标准（记住）

- **战术包** = 一个明确的单步能力，可以在几秒内完成、不需要"规划依赖图"；失败只需要本步重试/换参数。
- **战略包** = 需要选择目标、解析依赖、排序、跨多个战术、处理"缺料 → 去获取 → 再回来"这类分支。

制造满足后者：一个物品的配方是一棵**依赖树**（要材料 → 材料本身要合成/采集 → 需要工作站 → 需要移动到站 → 打开台子 → 批量合成 → 验证），所以是战略。

### 17.2 制造相关的战术清单（Batch B 真正要写的）

| 战术包 | 作用 | 对应 numen API | 类型 |
|---|---|---|---|
| `locate_station` | 找最近的工作台/熔炉（只读，返回位置） | `scan.blocks` | 只读 |
| `goto_station` | 移动到指定工作站（短移动段） | `move.to` | 短移动 |
| `open_station` | 右键打开工作站并确认窗口 | `use.block` | 交互 |
| `query_recipes` | 查某物品的所有配方（只读） | `inv.recipes` | 只读 |
| `query_craftable` | 查当前材料能做什么（只读） | `inv.craftable` | 只读 |
| `count_items` | 数背包里某物品数量（只读） | `inv.count` | 只读 |
| `craft_batch` | 在**已打开**的格子里做一次/一批并验证数量 | `inv.craft` | 单步写 |
| `smelt_batch` | 走到熔炉、放料、等待、取（分片长动作） | `inv.smelt` | 长动作（分片） |
