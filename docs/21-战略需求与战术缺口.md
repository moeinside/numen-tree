# 21. 战略需求 ↔ 战术缺口（活文档）

> 用法：一次只服务一个战略。先写"需要的战术清单"，对照现有库找缺口，只补这个战略要用的；战术齐了再写战略。
> 原则：**战略包只调用已测战术；缺什么补什么，不提前囤无关战术。**

## 3. 按战略拆战术：缺口分析

### 3.1 `bootstrap_kit`（建议第一个试点 L3）

**步骤**：采木头 → 做木板/木棍 → 做工作台 → 放工作台 → 做木镐/木斧/木剑 → 装备。

| 需要的战术 | 现有？ | 缺口 |
|---|---|---|
| 找树/找方块 | ✅ `locate_station`（可泛化为 find_block） | 需要通用化参数 |
| 走到目标 | ✅ `move_segment` | 寻路 no_path 兜底缺失 |
| 挖一小簇/砍一棵树 | ❌ | **`dig_cluster`**（已知簇，有界） |
| 捡掉落 | ❌（有 atom `collect_near`） | **`collect_drops`** 战术 |
| 做中间产物（木板/木棍） | ⚠️ `make_item` v1 不递归 | **v2 递归依赖** |
| 放工作台 | ❌ | **`place_one`** 战术 |
| 开工作台 | ✅ `open_station` | — |
| 做一批 | ✅ `craft_batch` | — |
| 装备武器/工具 | ❌（有 atom） | **`equip_best`** 战术 |
| 数量验收 | ✅ `count_items` | — |

**结论**：先补 `dig_cluster`、`collect_drops`、`place_one`、`equip_best`；`make_item` v2 递归可稍后（bootstrap 可手写子步骤）。

## 4. 缺口汇总（按批次）

**Batch C1（服务 bootstrap_kit）**
1. `dig_cluster`（已知簇，有界格数/时间）
2. `collect_drops`（半径收集掉落物）
3. `place_one`（放一个方块）
4. `equip_best`（换最好的武器/工具）
5. `find_block` 通用化（查任意方块/工作站）

**Batch C2（服务 prepare_for_night / build）**
6. `place_blueprint`（小段已知蓝图，≤64 格）
7. `sleep_once`（找床/睡到天亮）
8. `scan_container`（只读查容器内容）
9. `cook_batch`（用 smelt_batch 烤食物）
10. `no_path 兜底`（短距绕路/垫脚/退一步）

**Batch C3（战略层引擎）**
11. L3 project 状态 + decompose + 调度器 + 里程碑验收
12. `make_item` v2 递归依赖

## 5. 执行顺序（建议）

1. **Batch C1**（4~5 个战术）→ 实机 smoke；
2. 把 `bootstrap_kit` 迁成 L3 战略（此时战术齐）；
3. **Batch C2** → `prepare_for_night` L3；
4. 再 `build_safe_house` / `stockpile_food`；
5. 每补一批更新本文"现有/缺口"两栏。

## 6. 验收纪律

- 每个战术：离线自测 + 至少一次实机 smoke；
- 战略只调用已测战术；未知依赖直接拒绝启动；
- 一次只跑通一个战略，不并行铺开。

## 7. 战略设计规范：昼夜（用户要求，2026-11-08 23:1x）

> 用户：以后编战略包都要考虑白天/晚上不同战略。此条作为**强制设计规范**。

### 7.1 环境上下文（所有战略共享）

每个战略启动前/执行中都要读：
- `dark`：白天 / 夜晚；
- 距离天黑/天亮的时间（用 `game_time` 估算，避免"差 2 分钟天黑还去远征"）；
- 天气/雷暴（可选）；
- 威胁（敌对数量/距离）、HP/饥饿、离家距离。

### 7.2 战略注册表字段（以后每个战略必须声明）

```js
{
  timeOfDay: 'day' | 'night' | 'any',
  priorityByTime: { day: 40, night: 5 }, // 可选动态优先级
  nightFallback: 'wait' | 'return_home' | 'hold' | 'abort',
  duskCutoffSeconds: 120, // 天黑前多少秒不再启动"长/远"动作
  requiresDaylight: true|false,
}
```

### 7.3 昼夜行为约定

**白天**（安全档优先）：
- 允许：死亡点恢复、采集、合成、建造、探索、长途；
- 但接近黄昏：`duskCutoffSeconds` 内不启动新的长任务，优先回家/收尾。

**夜晚**：
- 禁止：远征、去远处死亡点、长距离探索、露天长时间合成；
- 优先：回家、守家、睡觉（有床）、就地合成/整理（基地安全时）；
- 战斗：有武器+血够 → 就地防御；没武器 → 往家/光走，不跑远；
- 等待：不安全时宁可 wait 到天亮，不送死。

**黄昏/黎明过渡**：
- 黄昏：停止"需要跨区"的战略，转 `return_home` / `prepare_for_night`；
- 黎明：重新允许白天战略（恢复装备/采集）。

### 7.4 与需求板的关系

- `night_chase` 只在夜晚激活，优先级 P1；
- `get_weapon/get_tools` 白天优先级更高；夜晚若必须做，只允许"基地内合成"变体，不允许远征；
- 所有需求/战略的 `done` 条件不依赖时间，但**执行路径**按昼夜切换。

### 7.5 现有战略补字段

| 战略 | timeOfDay | nightFallback | 说明 |
|---|---|---|---|
| `make_item` | any | hold | 基地内合成不分昼夜；远征采集分身 |
| `secure_gear` | day | wait | 夜里不出去捡/砍，等天亮 |
| `night_hold` | night | hold | 夜里回家/就地守 |

### 7.6 实现约定

- 新战略：先在注册表写 `timeOfDay/priorityByTime/nightFallback/duskCutoffSeconds`；
- lane 调度：按 `priorityByTime` 动态改目标优先级；`duskCutoffSeconds` 内拒绝"长/远"战略启动；
- 战术保持时间中立，时间判断只在战略/需求层做；
- 测试：每个战略至少覆盖 day/night 两条路径（离线 fixture）。

## 8. 下一战略：`prepare_for_night`（基地过夜/光照）

> 用户：基地过夜有点困难，需要光照？评估：光照是一个方向，但应先走**成本最低的过夜方案阶梯**，不要一上来就挖煤/烧炭。

### 8.1 过夜方案阶梯（按成本从低到高）

1. **有床 → 睡觉**：直接跳过夜晚（最便宜，优先）；
2. **有现成火把**（背包/箱子）→ 在基地周围放火把；
3. **有燃料**（煤/木炭）+ 木棍 → `craft_batch('minecraft:torch')` 做火把 → 放；
4. **没燃料** → 燃料链：
   - 有镐：挖煤（`dig_cluster('minecraft:coal_ore')`）；
   - 没煤/没矿：木镐→石镐→挖石头→熔炉→烧木炭（长链，最后做）；
5. **没床/没火把/没燃料** → 封闭基地（墙+门+屋顶）或回主人身边/换安全点；
6. 都不行 → 上报，夜里守/等天亮。

### 8.2 需要的战术/能力

| 能力 | 现有？ | 缺口 |
|---|---|---|
| 找床/床位置 | `locate_station('#minecraft:beds')` 可 | 无 |
| 睡觉 | `sleep_once` | 无 |
| 找火把/放火把 | `place_one`、`locate_station` | 需要"基地周围放点"的批量放置策略（`place_blueprint` 小段） |
| 查箱子火把 | `scan_container` + `fetch_batch` | 无 |
| 做火把 | `craft_batch`（recipe minecraft:torch） | 需要燃料/木棍前置 |
| 燃料链 | `dig_cluster`（煤）、`smelt_batch`（木炭）、`craft_batch`（熔炉） | 缺"先有镐/熔炉"的依赖规划（可先手写步骤） |
| 判断基地亮度 | 无 | 可用"基地周围火把数量"近似；numen 不一定暴露光照值 |
| 黄昏判断（提前准备） | 无 | 需要 game_time → 距离天黑估算 |

### 8.3 建议实现顺序

1. **`prepare_for_night` L3（v1）**：触发于夜晚/黄昏；顺序：床→现成火把→燃料做火把→否则上报；
2. 先做 `light_base` 子战略（放火把/做火把），床优先逻辑可内联；
3. 燃料链作为独立 L3（`fuel_chain`）后续补；
4. 封闭基地（`seal_base`）等 L3 建造能力齐了再做。

### 8.4 需要用户确认

- 当前"家"里有没有床？
- 有没有火把/箱子存货？
- 基地是封闭的（有墙/屋顶）还是露天的？
这决定 v1 先走"睡觉"还是"放火把"。

## 9. `prepare_for_night` 的拆分（用户问题：要拆吗？是循环监控事件吗？）

> 用户：需要拆分这个战略包吗？这是一个需要循环监控的重要事件吗？

**结论：要拆；它是"每日循环的需求（need）"，不是"一直跑的战略循环"。**

### 9.1 分层

```
need: night_safety（每日循环监控，轻量评估）
   ↓ 决定"现在要不要处理、多急"
strategy.prepare_for_night（L3 协调器，一次性执行）
   ├ strategy.sleep_through_night（有床）
   ├ strategy.light_base（有火把/燃料）
   ├ strategy.fuel_chain（没燃料，长链，后续）
   ├ strategy.seal_base（封闭基地，后续）
   └ strategy.return_home（人在外面）
   ↓
战术：sleep_once / place_one / craft_batch / scan_container / travel_to ...
```

### 9.2 为什么不能做成"循环战略"

- 战略应该**一次性、有验收、几秒~几十秒**；把"监控"写进战略会导致长期占 tick、每 tick 重跑；
- 监控应该放在 **need 层**：每 5~10 秒（或观测后）评估一次，轻量、无副作用；
- 只有 need 判定"该处理且可执行"时，才启动协调器战略；完成后 need 重新评估，满足则休眠到下一个黄昏/夜晚。

### 9.3 need: night_safety 设计

```js
{
  id: 'night_safety',
  level: 3,
  when: state => 接近黄昏/夜晚 且 基地不安全（无床/无光/不封闭）,
  priority: (state, opt) => {
    // 白天低，黄昏逐渐升高，夜里最高
    // 无床/无光/不封闭 + 有怪 → P1
  },
  done: state => 基地安全（有床 或 足够火把 或 已封闭）,
  strategies: ['prepare_for_night'],
  cooldownSeconds: 60,
}
```

需要的数据：
- 距离天黑的时间（`game_time` 估算；黄昏前 N 秒开始准备）；
- 基地资产缓存：床/火把数量/墙/屋顶/箱子（由 `inspect_base` 只读检查，不每 tick 扫）；
- 当前是否在基地、附近敌对。

### 9.4 协调器 `prepare_for_night` 的职责

1. 先 `inspect_base`（只读，结果缓存）；
2. 按成本阶梯选子战略：
   - 有床 → `sleep_through_night`；
   - 有火把/箱子有火把 → `light_base`；
   - 有燃料 → `light_base`（做火把）；
   - 没燃料 → `fuel_chain`（后续）；
   - 都不行 → `seal_base` 或上报；
3. 只执行一个子战略，完成后返回；need 再评估是否还需要下一步。

### 9.5 与其他需求的关系

- `night_chase`（正在被追）优先级高于 `night_safety`；
- `get_weapon/get_tools` 夜里可让位给 `night_safety`（先活过今晚），白天再补装备；
- 白天准备（pre-dusk）优先级低于白天生产，但高于闲置。

### 9.6 实现顺序（建议）

1. `inspect_base` 只读战术（床/火把/墙/箱子，带缓存）；
2. `night_safety` need（含黄昏时间估算）；
3. `prepare_for_night` 协调器 + `sleep_through_night` / `light_base`；
4. `fuel_chain` / `seal_base` 后续。
