## 1. 最重要的发现：mod 里已经有一个"小脑"

我们原本以为要自建的反射层、恢复阶梯、任务系统，**mod 内部已经有了**。

| 组件 | 类 | 含义 |
|---|---|---|
| 同伴大脑 | `task.CompanionBrain` | 每同伴一个，按游戏 tick 驱动；含 `sync` / `current` 两个任务槽、`reflexes` 列表、`idlePoses`、`TaskPersistence$LeftOver` |
| 任务接口 | `task.Task` | `canRun` / `prepare` / `start` / `tick` / `stop` / `result` / `name` |
| 任务选择 | `task.TaskSelector.select(...)` | 在反射、当前任务、待机姿态之间挑一个 |
| 任务槽 | `task.TaskSlot` | `canRun` / `put` / `tick` / `cancel` / `freeze` / `settleIfTerminal` |
| **恢复阶梯** | `core.task.base.RecoveryLadder` | `Rung(strategy, handles:Set<FailureType>, maxAttempts)`，`advance(FailureType)`、`exhausted()` |
| 前置条件 | `core.task.base.Precondition` + `$Failure` | 开始前校验 |
| 反射链 | `core.task.chain.*` | `UnstuckChain`（脱困）、`FleeChain`（逃跑）、`MLGChain`（落地缓冲）、`MobDefenseChain`（防御）、`BreathChain`（憋气） |
| 反射注册 | `task.reflex.ReflexRegistry` / `Reflex` / `PolicyReflex` | 可注册、可枚举（`overview()`） |
| 内置反射与生存 | `core.task.reflex.CoreReflexes`、`core.task.survival.SurvivalDecisions` | |
| 任务持久化 | `task.TaskPersistence` | `remember/forget/leftOver/replay` —— **跨程序的对象已经存在** |
| 寻路 | `pathing.**` | 含 `Watchdog`、`ParkourControl`、`PillarControl`、`Outcome` 细分（NoRoute/Blocked/OutOfBudget/…） |
| 权限/同意 | `permission.**` | `Gate`、`Rule`、`Verdict`、`ConsentDesk`、`Mode` —— **现成的危险动作闸门** |
| 插件 SPI | `api.NumenPlugin` / `api.NumenApi` | 见 `04-可扩展性设计.md` |

**设计影响：树不需要自己实现"怎么跳、怎么挖、怎么脱困"，那是 mod 的活。树的活是"决定现在做什么"，并且它现在没人做。**

## 2. Lua 程序模型（僵尸锁与分片的基础）

### 2.1 程序是 tick 驱动的、可中断的

`com.dwinovo.numen.program.ServerPrograms`：

```
RUNNING : Map<UUID, Running>        // 每个同伴一条
run(...) / launch(...)              // 启动
admit(player, owner, companion)     // 准入检查，返回拒绝原因（"a program is already running…" 出处）
tick() / pump()                     // 每 tick 推进
idle(UUID) / running(UUID)          // 状态查询
interrupt(UUID, String, String)     // 中断
cutOff(UUID, String, boolean)       // 切断（"this turn was cut off" 出处）
stop(NumenPlayer)                   // 停止
ownerLeft(UUID) / dropAll()         // 主人离开时清理
watch(UUID, EventQueue$Entry)       // 监听事件（主人说话可打断）
```

`Running` 持有：`companion`、`owner`、`programId`、`lane`(MainQueue.Lane)、`client`、`program`、`claimed`。

### 2.2 时间片与超时常量

`com.dwinovo.numen.program.ProgramLimits`（javap -constants 实测）：

| 常量 | 值 | 含义（推断） |
|---|---|---|
| `PER_OWNER` | 8 | 每主人并发程序上限 |
| `SERVER_WIDE` | 64 | 全服并发上限 |
| `TICK_NANOS_ALL` | 10 ms | 每 tick 分给所有程序的 CPU 预算 |
| `TICK_NANOS_PER_PROGRAM` | 5 ms | 每 tick 单个程序的 CPU 预算 |
| `CLIENT_ANSWER_TICKS` | 600 tick | 客户端应答超时 = **30 秒**（20 tps） |
| `MODULE_CACHE_BYTES` | 4 MB | 模块缓存上限 |

`MainQueue` 有 `lane()` / `drain(纳秒, 纳秒)` / `drainAll()` —— 程序在**主线程上分时片运行**，不会卡服。

### 2.3 任务查询/停止接口（Lua 已有）

`com.dwinovo.numen.task.TaskApi`：

```java
status(ServerCall) -> Status { taskId, task, state, elapsedS, budgetLeftS, timers[] }
stop(ServerCall, Stop { taskId }) -> Stopped
timer(ServerCall, SetTimer) -> ...
```

⇒ **`numen.task.status()` 能拿到当前任务、状态、已用时、剩余预算**。这是树上行观测最便宜的一手数据。

## 3. Lua 实现层（`config/numen/lua/<id>/numen/*.lua`）

这些是**可读的实现源码**，不是二进制。已确认：

- `move.to(target, spec)` = `route.plan(spec)` + `move.go(plan)`，**一次调用就是一个完整的走+恢复任务**。
- `route.plan` 支持 `arrive / range / stops / mode / costs / avoid / materials`。
- `move.explore(dir, {until_, seconds, hop})` —— **就是"有预算的循环"的官方范例**：`while walked < seconds`，每轮规划+走一跳，超预算返回。⇒ 分片写法在 Lua 侧是成立的。
- `work.mine(cluster)` 是自带的宏循环：走近→挖→捡→直到挖完；单轮没进展就 `raise("failed", …)`。
- 错误是结构化的：`raise(kind, message, hint, data)`，外部拿到 `err.kind` / `err.hint` / `err.data`。**`err.data` 里已经带计划、剩余、最近目标等事实**，可直接做上报字段。
- `time.wait_until(fn, {every, timeout})` 提供超时轮询。
- **没有独立的"跳"原语**：跳跃是 `move.go` 内部的寻路行为。用户观察到的"单独执行跳"，要么是 LLM 手动小步 `move.to`，要么是任务被切断后重启。

## 5. 僵尸锁分析

### 5.1 已知事实

- 锁是 `ServerPrograms.RUNNING` 里的**内存标记**，按 companion UUID。
- 释放路径：程序自然结束 / 被 `interrupt` / 被 `cutOff` / 被 `stop` / `ownerLeft` / `dropAll`。
- **MCP 的 9 个工具里没有任何一个能触发 `stop`**（`numen.task.stop()` 停的是任务，不是程序）。
- 主人说话会触发 `watch(...)` → 可打断程序（这也是文档里"请主人说句话"的原理）。

### 5.2 两个可能成因

| 假设 | 依据 | 验证方式 |
|---|---|---|
| **A. 程序被遗弃但线程未回收** | 客户端断开后 `RUNNING` 未清理；此前现象是"一直不释放" | 活体：跑一个长程序，kill 客户端，观察 `numen.task.status()` / 再次 `lua` 的拒绝文案 |
| **B. 内置大脑占着同伴** | 拒绝文案是 "…**or its built-in brain is acting**"；而 `binding.json` 里确实绑了 provider | 检查该同伴的 `binding.json`；在游戏内解绑 provider 后再试 |

> **B 是被忽略的一条**：`config/numen/companions/*/binding.json` 里带 `provider` 字段，说明内置脑可能在被触发时占住这个同伴。

### 5.3 当前结论

**从外部无法清除该锁**（无 stop 入口，且不写 mod 文件）⇒ 因此**不写入 mod 目录**。
策略改为**不产生锁**：

1. 树**永不遗弃在途调用**（客户端侧不做 kill / 不做超时会话中断）。
2. 所有 `lua` 调用必须自带 `deadline`，程序自己结束。
3. 分片控制在 10–20 秒，远小于 30 秒的 `CLIENT_ANSWER_TICKS`。
4. 收到拒绝文案时，**按 B 先查 binding**，再按 A 处理（等 20 分钟 / 重建同伴）。

## 6. 活体探针结果（2026-11-07，游戏运行中）

环境：同伴 `tyrander`（id `97294ad3-…`），主人 `moeisnide` 在线，**创造模式**，桦树林。

| # | 问题 | 结论 |
|---|---|---|
| 1 | 程序运行中，第二个 `lua` 能否进 | ❌ **被拒**：`a program is already running for this companion, or its built-in brain is acting` |
| 2 | 程序运行中，非 lua 工具能否用 | ✅ **`get_events` / `say` / `list_companions` 全部可用** |
| 3 | 正常结束后槽位是否释放 | ✅ 干净释放，无僵尸锁 |
| 4 | 阻塞语义 | ✅ 阻塞。`plan.seconds` 预估 vs 实测：**7.9s→7.2s**、**5.9s→7.2s**（约 ±20%） |
| 5 | 沙箱能力 | ❌ **没有 `os` 库**。时钟只能用 `numen.time.wait`（返回实际秒，最小 0.1s）或 `status.world().game_time`（世界刻，20/s） |
| 6 | 工具返回长度 | 单个长字符串被截断到约 300 字符；需要长文本时返回 ≤220 字符的切片数组 |
| 7 | 自动改地形 | ✅ 走路时按 `costs.place` 自动垫了 2 个圆石（消耗背包） |

**第 2 条是本次最重要的架构结论**：

> 树的观测与说话**不需要** Lua 槽，只有"动作"需要。
> ⇒ 树可以在同伴干活期间自由 `get_events` / `say`，只有下一条动作指令要等槽空出来。

### 6.1 任务模型（帮助文本原话）

- `move.go` / `work.dig` / `move.follow` 都是 **"后台工作（background work）"**：程序会等它结束，然后拿到返回值。
- **"a task left running when a program stopped ends with a `task_finished` event"** —— 程序被停止时，任务继续跑，结束时以事件收尾。
- `numen.task.status()` → `{task_id?, task?, state?("running"|"queued"), elapsed_s?, budget_left_s?, timers[]}`
- `numen.task.stop({task_id?})` → 不带 id 就停"后台任务"，"so the body frees up"。
- 定时器：最多 8 个，1–1200 秒（世界时间）。

⇒ **执行模型可以简化**：树不需要自己造"分片循环"，因为 mod 的任务本身就带边界（`move.go` 到目的地即止、`dig({count})` 挖够即止、`follow({seconds})` 到点即止），且内部已经有 `RecoveryLadder` / `UnstuckChain` 处理卡住。
**树要做的是：一次调用放一个任务 → 拿到终态 → 决定下一个。** 这比"10–20 秒切片"更简单，也更贴合 mod 的设计。

### 6.2 "主人说话打断"实验：通过（结果决定性）

实验：树侧起 `numen.move.follow(nil, {distance=3, seconds=60})`，主人在游戏里说一句话（"gg"）。

| 观测 | 结果 |
|---|---|
| 程序 | **6.2 秒就被打断**（没有等满 60 秒） |
| 返回文案 | `your owner spoke; **t3 keeps running**. Nothing after that ran.` |
| 打断后任务 | ✅ 继续跑：`{task_id="t3", task="numen.move.follow", state="running", elapsed_s=13, budget_left_s=65}` |
| 打断后槽位 | ✅ **空出来了**——期间成功执行了新的 `lua`（只读） |
| 再派新任务 | ✅ 新任务立刻执行（<1 秒）；**旧任务被取代**，`after` 里 `t3` 消失 |
| 被取代的事件 | `<event kind="task_finished" id="t3" task="numen.move.follow" status="stopped">a newer body action replaced it — interrupted</event>` |

## 7. 执行模型（最终确认）

```
① 树用一次 lua 调一个任务    →  程序阻塞等任务结束
② 主人说话 / 程序被打断      →  程序立刻返回，任务继续在后台跑
③ 后台任务在跑时            →  Lua 槽是空的：
                               · 只读 lua（task.status / status.*）可以跑
                               · get_events / say 也可以跑
④ 树想改主意               →  直接派新任务，旧任务自动被取代
                               （task_finished / status=stopped）
⑤ 任务结束                 →  task_finished 事件进收件箱
```

### 由此得到的三条简化

**1. 不需要"切片器"。**
任务自带边界（`move.go` 到目的地即止、`dig({count})` 挖够即止、`follow({seconds})` 到点即止），内部还有 `RecoveryLadder` / `UnstuckChain`。树只要"一次一个任务，拿终态，决定下一个"。

**2. 不需要"cancel 原语"。**
抢占 = 直接派新任务。旧任务自动 `stopped` 并留下事件，不需要先停再派。

**3. 上行通道天然存在。**
`task_finished` 事件就是"完成上报"，已经带 `id` / `task` / `status` / 原因。树不用自己编一套完成信号，只需要补上"需要 LLM 决策时"的分类。

### 对树进程的含义

- 树的动作队列**不需要很复杂**：每个同伴一条串行队列，队列里放"任务"，一个接一个。
- 树的下发调用可以**同步等待**（因为它是异步进程，等待不阻塞别人），也可以在被打断后靠事件收尾。
- **观测永远是 `get_events`，不走 lua**——这条要写进实现纪律。
